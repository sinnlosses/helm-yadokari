## 確定した決定事項

### 目的・スコープ

- **目的**: Helm chart でバージョン管理されているアプリケーションのバージョンを、
  自動で最新に更新・メンテナンスするシステム。
- **想定利用者**: チーム内限定（社内複数チームが利用する前提の汎用システム）。
- **対象範囲**: 単一アプリ専用ではなく、複数チームが使うことを想定した
  汎用システム。複数の Helm chart・複数の GitLab プロジェクトを横断的に扱える設計。

### 更新ワークフロー

- **更新対象**: `values.yaml` 内のコンテナイメージタグをアプリの最新版に書き換え、
  Git（GitLab）へコミットし MR（Merge Request）を作成する。
  クラスタへの直接 `helm upgrade` は行わない（GitOpsスタイル）。
- **「最新版」の判定元**: GitLabのタグ。タグは特定のブランチから切られており、
  命名パターンからどのブランチ由来か判別できる。タグ名には打刻日時も含まれる。
  → **具体的なタグ命名フォーマットは未確定（保留中、下記オープン参照）**。
- **追跡対象ブランチ**: 固定ブランチではなく、アプリ（chart）ごとに
  追跡対象ブランチを設定可能にする。
- **リポジトリ構成**: Helm chart（`values.yaml`）を管理する GitLab プロジェクトと、
  タグが打たれるアプリのソースコードの GitLab プロジェクトは別々。
- **values.yaml内のイメージタグ位置**: 固定パス規約ではなく、アプリ（chart）ごとに
  YAMLパス（dotパス等）を設定可能にする。
- **複数アプリの処理単位**: pipeline schedule 1回の実行で登録済み全アプリを
  まとめて処理する（個別実行には分けない）。
- **1アプリ失敗時の挙動**: 他のアプリの処理は継続する。最後に失敗一覧をサマリー表示し、
  CLI全体の終了コードは失敗有無で非ゼロにする（1アプリの障害が他チームをブロックしない）。

### MR・ブランチ運用

- **ブランチ命名・MR更新方針**: 固定ブランチ名（例: `yadokari/<app名>`）を使う。
  すでにそのブランチ/MRがオープンな間は、新しいタグが出ても更新せず放置し、
  マージ（またはクローズ）されるまで次の実行はスキップし続ける。
  マージ済み・MR無しの場合のみ、新しいタグでブランチを作り直してMRを作成する。
- **MRの反映先と承認フロー**: `values.yaml` の更新は chart/values 管理リポジトリに
  対して MR を作成する。自動マージはせず、人間のレビュー承認を必須とする。
- **通知**: 専用の通知（Slack等）は不要。GitLab標準のMR通知に任せる（MVP方針）。

### 実行環境

- **実行形態**: CLIツール。GitLab CI の pipeline schedules から定期実行する想定。
  （GitHub Actionsではなく GitLab CI）
- **実装言語**: TypeScript。
- **配布方法**: CI job上で npm install する方式（Dockerイメージ配布ではない）。
  公開npmレジストリ（npmjs.com）に公開する。
- **Node.jsバージョン**: 現時点でチーム標準がなければ、その時点のNode.js LTSを
  `package.json` の `engines` で明示し、CI側のベースイメージで揃える。
- **GitLab認証方式**: `CI_JOB_TOKEN` ではなく、スコープを絞った Group Access Token を
  CI/CD変数（masked）として渡す（複数プロジェクトを横断操作するため）。

### 運用・登録フロー

- **アプリ登録のフロー**: 各チームがCLIリポジトリの設定ファイルへMRを送り、
  レビュー後マージするセルフサービス方式。

### 変更なし時・MR内容・並列実行・セキュリティ・Dry-run（6ラウンド目）

- **変更なし時の挙動**: 最新タグが反映済みタグと同じ場合はMRを作らないが、CLIログには
  判定結果を出力する。
- **MRの内容**: アプリ名・旧タグ→新タグ・タグの打刻日時・タグへのGitLabリンクに加えて、
  そのタグ（push）に紐づくGitLab CIパイプラインへのリンクを含める。パイプラインの状態は
  情報提供のみ（MR本文に記載）で、成功/失敗によるフィルタリングはしない。マージ判断は
  レビュアーに委ねる。
- **並列実行制御**: `p-limit` で同時実行数を制御。デフォルト3〜5、設定で上書き可能。
- **トークンスコープ**: `read_api` + `write_repository` + MR作成権限相当に限定（最小権限）。
- **Dry-runモード**: 用意する。実際のブランチ作成・MR送信をせず更新予定内容だけ確認できる。

### タグ命名規則・設定ファイル構成の確定（7ラウンド目）

- **タグ命名規則**: `${追跡ブランチ名の"/"を"-"に置換した値}-build-at-${yyyymmdd}-${hhmmss}`
- **設定ファイル構成**: `config/<chartリポジトリ名>/chart.yaml` + `config/<chartリポジトリ名>/
<tenantId>/<clientId>/apps.yaml` という2階層固定のディレクトリ構成。実物は
  `config/teamA-chart/` 配下を参照。CLIは `config/` を再帰的に走査して全`apps.yaml`を処理する。

### MRの粒度・チャートリポジトリ単位への集約（8〜9ラウンド目）

- **MRの粒度**: アプリ単位ではなく **chartリポジトリ単位** で1つのMRに集約する
  （GitLabのMRはプロジェクト単位でしか作れないため）
- **ブランチ名**: chartリポジトリごとの固定値（例: `yadokari/update`）。アプリ名や
  テナント/クライアントIDは含めない
- **既存MRオープン中の挙動**: そのchartリポジトリ全体の更新処理をスキップする
  （他のchartリポジトリには影響しない）
- **部分失敗時の挙動**: 同じchartリポジトリ内で一部アプリの処理が失敗した場合、
  成功した分だけを反映するのではなく、そのchartリポジトリ全体をオールオアナッシングで
  見送る（MRを作らない）。chartリポジトリ間では失敗しても他は継続する

### 実装後の訂正: 追跡ブランチにタグがない場合の挙動

- 実装（骨格）完了後のレビューで、ユーザーから訂正あり: 「追跡ブランチ由来の最新タグがない場合、
  タグを作り、それを values.yaml に設定する」。当初の実装・README・要件定義は「見つからない場合は
  ERROR（chart全体を見送り）」としていたが誤りだった
- 追跡ブランチの最新コミットに対して、CLI自身がタグ命名規則に従った新しいタグを作成し、
  それを最新タグとして扱う。`DRY_RUN=true` のときは実際の作成をスキップする
- `docs/requirements.md` 4.1節、`README.md`（Features・仕組み図・エラーハンドリング表）、
  `src/lib/tag.ts`（`buildNewTag`）・`src/lib/gitlab.ts`（`createTag`）・`src/main.ts` に反映済み

### タグ命名規則の設定可能化

- 7ラウンド目で固定と確定していたタグ命名規則を、ユーザーからの依頼「ブランチ由来のタグの
  形式を決め打ちではなく設定可能にできるか」を受けて再検討
- 設定の粒度: app単位（config.yaml側）ではなく、全体で1つの環境変数（`TAG_FORMAT`）にする
  と決定。branchToSyncのようなapp単位の設定にはせず、ソースリポジトリごとの命名規則の
  ばらつきには対応しない（そこまでの要望は無かったため）
- 柔軟性のレベル: 正規表現による既存タグ解析のみのカスタマイズ案もあったが、新規タグ作成
  （`buildNewTag`）にも使えるテンプレート文字列方式（`{branch}`/`{date}`/`{time}`
  プレースホルダを含む）を採用。既存の固定フォーマットをそのままデフォルト値にすることで
  後方互換を保つ
- 運用上の注意点として、フォーマットを運用途中で変更すると過去に作成済みのタグが追跡ブランチ
  由来のタグとして認識されなくなる旨をREADMEに明記した

### MRの分割単位をtenantId/clientId単位に変更

- 8〜9ラウンド目で確定していた「MRはchartリポジトリ単位」を、ユーザーからの提案
  「MRを出す単位をclientIdごとにしようと思うんだけどどうかな?」を受けて再検討。
  実装側から動機を確認したところ「マージしたいclientと保留したいclientがいそう」との回答。
  現状（`config/teamA-chart/tenantId1/clientId1/`等）はどのchartディレクトリもtenantId/
  clientIdが1組しかなく、この変更をしても既存の実例の挙動自体は変わらない（将来1つの
  chartリポジトリに複数クライアントが乗る運用への備え）
- **MRの粒度**: chartリポジトリ単位 → `(chartディレクトリ, tenantId, clientId)`単位に変更。
  1つのchartリポジトリに複数のtenantId/clientIdがある場合、クライアントごとに独立した
  ブランチ・MRになる
- **ブランチ名**: 固定値`yadokari/update`を廃止し、`feature/yadokari/<tenantId>/<clientId>`
  に変更（同一GitLabプロジェクト内で複数MRが共存するため、IDを含める必要がある）
- **tenantId/clientIdがGitLabブランチ名として不正な文字を含む場合**: 追加のバリデーションは
  行わない。既存の「非fatalなAPIエラーは該当分だけERRORとしてログ記録し処理継続」という
  方針に任せ、そのクライアントだけがERRORになる（他のクライアント・chartリポジトリには影響しない）
- **MRタイトル**: `Auto MR by yadokari: update ${tenantId}/${clientId} ${N} app image tag(s)`
  （同一プロジェクトに複数MRが並ぶため、タイトルだけで見分けられるようにする）
- **オールオアナッシングの範囲**: chartリポジトリ全体 → そのクライアント内の全アプリに縮小。
  ある1クライアントの失敗が、同じchartリポジトリの他クライアントの更新をブロックしなくなる
  （今回の変更の主目的）
- **既存MRオープン中の挙動**: クライアントの固定ブランチ単位で判定し、そのクライアントの
  更新処理だけをスキップする（他クライアント・他chartリポジトリの処理には影響しない）
- **異なるclientが同じ`values.yaml`を共有するケース**: 今の実装は同じ`valuesPath`を複数
  アプリで共有する場合に1ファイルの書き換えとしてまとめる仕組み（`valuesYamlCache`）を
  持っており、これは元々「同じchartリポジトリ内の複数client分を1MRにまとめる」設計を前提に
  作られたもの。MRをclient単位に分けると、異なる2つのclientが同じ`valuesPath`を参照している
  場合に、それぞれ別ブランチ・別MRで同じファイルを独立に書き換えることになり、マージ順に
  よっては片方の変更が食い違う可能性がある。追加のバリデーションは行わず、既知の制限として
  ドキュメントに明記するのみとする（tenantId/clientIdはそもそもアプリ設定を分割管理する単位
  のため、異なるclientが同じ`values.yaml`を参照するケースは運用上ほぼ想定されない）
- **`CONCURRENCY_LIMIT`の意味**: 「chartリポジトリの同時処理数」から
  「`(chartディレクトリ, tenantId, clientId)`単位の同時処理数」に定義し直す。chartリポジトリ・
  client単位の2段階の同時実行数制御は導入しない（GitLab側のレート制限は基本的にトークン単位
  でありプロジェクト単位ではないため、複雑さに見合わない）
- **同じtenantId/clientIdが複数のchartディレクトリにまたがる場合**: 従来からchartディレクトリ
  単位で別MRだったため、この変更による影響はない（既存動作のまま）
- 要件定義のみで本ラウンドは完了とし、実装は別タスクに切り出す（このプロジェクトでこれまでも
  採ってきた進め方）。
  `docs/requirements.md` 2.1節・4.2節・4.3節を本ラウンドの内容に更新済み。コードは未着手
  （`src/types.ts`のChartAndApps型・`src/lib/config.ts`のグルーピング・`src/lib/gitlab/gitlab.ts`の
  `UPDATE_BRANCH`・`buildMrTitle`等が変更対象になる見込み）

### 固定ブランチの再作成漏れの修正

- 前段の「MRの分割単位をtenantId/clientId単位に変更」のセッションでユーザーから「以前指摘して
  いた更新ブランチ名の見直しはもはや問題ないんじゃないか。定期実行後に手動実行したくなったら、
  定期実行で作られたMRを閉じればいい」との指摘。ただし「MRをクローズしてもブランチが残り続ける
  仕様になっているなら、MRが存在しない
  のにブランチが存在する場合は削除する仕様にしたい」という追加要望
- 調査の結果、`docs/requirements.md`には元々「マージまたはクローズされた後の実行で、改めて
  固定ブランチを作り直しMRを作成する」と明記されていた（8〜9ラウンド目）にもかかわらず、
  実装（`commitFileUpdates()`）はブランチが存在する場合は削除せず追加コミットを積むだけに
  なっており、要件と実装が食い違っていた（ドキュメント通りに実装されていなかったバグ）
- 修正方針: `commitFileUpdates()`の呼び出し元（`filterTargets`）が「このブランチにオープン中
  のMRが無い」ことを既に確認済みという前提を活かし、ブランチが存在すれば無条件で削除してから
  `mrTargetBranch`を起点に作り直す。ファイルごとのaction（create/update）判定も、以前は
  「ブランチが存在すればそのブランチ、なければbaseBranch」を参照していたのを「常にbaseBranch」
  に単純化した（ブランチは常に作り直す前提になったため）
- マージ済み・クローズ済みのどちらの場合も同じ扱い（無条件で削除）でよいと判断。マージ済みなら
  変更は既にmrTargetBranchに取り込まれているため削除は無害、クローズ済みなら人間が明示的に
  却下した変更なので復元する必要がない
