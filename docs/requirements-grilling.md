このファイルは `/grilling` セッションの途中経過。会話が途切れても、ここを読めば
どこまで決まっていて、次に何を聞くべきかが分かるようにする。

## 確定した決定事項

### 目的・スコープ

- **目的**: Helm chart でバージョン管理されているアプリケーションのバージョンを、
  自動で最新に更新・メンテナンスするシステム。
- **想定利用者**: チーム内限定（社内複数チームが利用する前提の汎用システム）。
- **対象範囲**: 単一アプリ専用ではなく、複数チームが使うことを想定した
  汎用システム。複数の Helm chart・複数の GitLab プロジェクトを横断的に扱える設計。

### 更新ワークフロー

- **更新対象**: `values.yaml` 内のコンテナイメージタグをアプリの最新版に書き換え、
  Git（GitLab）へコミットし MR（Merge Request）を作成する。
  クラスタへの直接 `helm upgrade` は行わない（GitOpsスタイル）。
- **「最新版」の判定元**: GitLabのタグ。タグは特定のブランチから切られており、
  命名パターンからどのブランチ由来か判別できる。タグ名には打刻日時も含まれる。
  → **具体的なタグ命名フォーマットは未確定（保留中、下記オープン参照）**。
- **追跡対象ブランチ**: 固定ブランチではなく、アプリ（chart）ごとに
  追跡対象ブランチを設定可能にする。
- **リポジトリ構成**: Helm chart（`values.yaml`）を管理する GitLab プロジェクトと、
  タグが打たれるアプリのソースコードの GitLab プロジェクトは別々。
- **values.yaml内のイメージタグ位置**: 固定パス規約ではなく、アプリ（chart）ごとに
  YAMLパス（dotパス等）を設定可能にする。
- **複数アプリの処理単位**: pipeline schedule 1回の実行で登録済み全アプリを
  まとめて処理する（個別実行には分けない）。
- **1アプリ失敗時の挙動**: 他のアプリの処理は継続する。最後に失敗一覧をサマリー表示し、
  CLI全体の終了コードは失敗有無で非ゼロにする（1アプリの障害が他チームをブロックしない）。

### MR・ブランチ運用

- **ブランチ命名・MR更新方針**: 固定ブランチ名（例: `yadokari/<app名>`）を使う。
  すでにそのブランチ/MRがオープンな間は、新しいタグが出ても更新せず放置し、
  マージ（またはクローズ）されるまで次の実行はスキップし続ける。
  マージ済み・MR無しの場合のみ、新しいタグでブランチを作り直してMRを作成する。
- **MRの反映先と承認フロー**: `values.yaml` の更新は chart/values 管理リポジトリに
  対して MR を作成する。自動マージはせず、人間のレビュー承認を必須とする。
- **通知**: 専用の通知（Slack等）は不要。GitLab標準のMR通知に任せる（MVP方針）。

### 実行環境

- **実行形態**: CLIツール。GitLab CI の pipeline schedules から定期実行する想定。
  （GitHub Actionsではなく GitLab CI）
- **実装言語**: TypeScript。
- **配布方法**: CI job上で npm install する方式（Dockerイメージ配布ではない）。
  公開npmレジストリ（npmjs.com）に公開する。
- **Node.jsバージョン**: 現時点でチーム標準がなければ、その時点のNode.js LTSを
  `package.json` の `engines` で明示し、CI側のベースイメージで揃える。
- **GitLab認証方式**: `CI_JOB_TOKEN` ではなく、スコープを絞った Group Access Token を
  CI/CD変数（masked）として渡す（複数プロジェクトを横断操作するため）。

### 運用・登録フロー

- **アプリ登録のフロー**: 各チームがCLIリポジトリの設定ファイルへMRを送り、
  レビュー後マージするセルフサービス方式。

### 変更なし時・MR内容・並列実行・セキュリティ・Dry-run（6ラウンド目）

- **変更なし時の挙動**: 最新タグが反映済みタグと同じ場合はMRを作らないが、CLIログには
  判定結果を出力する。
- **MRの内容**: アプリ名・旧タグ→新タグ・タグの打刻日時・タグへのGitLabリンクに加えて、
  そのタグ（push）に紐づくGitLab CIパイプラインへのリンクを含める。パイプラインの状態は
  情報提供のみ（MR本文に記載）で、成功/失敗によるフィルタリングはしない。マージ判断は
  レビュアーに委ねる。
- **並列実行制御**: `p-limit` で同時実行数を制御。デフォルト3〜5、設定で上書き可能。
- **トークンスコープ**: `read_api` + `write_repository` + MR作成権限相当に限定（最小権限）。
- **Dry-runモード**: 用意する。実際のブランチ作成・MR送信をせず更新予定内容だけ確認できる。

### タグ命名規則・設定ファイル構成の確定（7ラウンド目）

- **タグ命名規則**: `${追跡ブランチ名の"/"を"-"に置換した値}-build-at-${yyyymmdd}-${hhmmss}`
- **設定ファイル構成**: `config/<chartリポジトリ名>/chart.yaml` + `config/<chartリポジトリ名>/
<tenantId>/<clientId>/apps.yaml` という2階層固定のディレクトリ構成。実物は
  `config/teamA-chart/` 配下を参照。CLIは `config/` を再帰的に走査して全`apps.yaml`を処理する。

### MRの粒度・チャートリポジトリ単位への集約（8〜9ラウンド目）

- **MRの粒度**: アプリ単位ではなく **chartリポジトリ単位** で1つのMRに集約する
  （GitLabのMRはプロジェクト単位でしか作れないため）
- **ブランチ名**: chartリポジトリごとの固定値（例: `yadokari/update`）。アプリ名や
  テナント/クライアントIDは含めない
- **既存MRオープン中の挙動**: そのchartリポジトリ全体の更新処理をスキップする
  （他のchartリポジトリには影響しない）
- **部分失敗時の挙動**: 同じchartリポジトリ内で一部アプリの処理が失敗した場合、
  成功した分だけを反映するのではなく、そのchartリポジトリ全体をオールオアナッシングで
  見送る（MRを作らない）。chartリポジトリ間では失敗しても他は継続する
