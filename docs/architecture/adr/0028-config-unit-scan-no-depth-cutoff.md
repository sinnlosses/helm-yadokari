# 設定ユニットの走査は深さで打ち切らず、絞り込みより先に階層を検証する

深さ1〜2に限ること・入れ子を禁じることの理由は `docs/requirements.md` 4.4節が正典。ここに
書くのは、その規則を `loadConfig()` でどう実装したかの判断だけ。

- **走査を深さ2で打ち切らず、chartディレクトリ配下を全部見る**。打ち切ると深さ3以上に置かれた
  設定ユニットが「設定エラー」ではなく「対象0件」として黙って無視され、書いた本人が
  気づけない。走査は`readdir`と`versions.yaml`・`locations.yaml`の存在確認だけでYAMLを読まないので、全部見ても
  実行時間はほぼ変わらない
- **入れ子は走査中ではなく、走査結果の`unitPath`同士の突き合わせで判定する**。深さ0・深さ3以上の
  判定と同じ1箇所に並ぶため。「見つけた`unitPath`同士しか見ないので深い位置の設定ユニットを
  拾えない」というこの方式の弱点は、走査を深さで打ち切らないことで消してある
- **階層の検証は`TARGET_UNITS`の絞り込みより前に、対象外の設定ユニットも含めて行う**。絞り込み
  実行でしか通らない検証を作らないため。一方で`versions.yaml`・`locations.yaml`の読み込みは
  絞り込んだ後だけに行う。無関係なチームのYAMLの設定ミスで緊急時の限定実行まで
  止めないため（全設定ユニットのYAMLは、`target`を指定しない`pnpm lint:validate-config`が
  MR時点で読む）
- **`TARGET_UNITS`の実在チェックは、走査で見つかった`unitPath`との照合で行う**（ディレクトリの
  有無では足りない）。深さが可変なので「ディレクトリはあるが
  2ファイルがそろっていない」「深さ2の設定ユニットの中間ディレクトリを指している」が紛れ込み、
  どちらも「設定ユニットとしては存在しない」と報告するのが正しいため。この照合を通った
  `unitPath`は必ず2ファイルを持つので、設定ユニットの読み込み処理は2ファイルの有無を
  再確認せず設定ユニット1件を必ず返す
