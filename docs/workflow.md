# 進捗管理とHandoffの詳細

`CLAUDE.md`の「進捗管理とHandoff」節で触れている `tasks.json` / `progress.md` のフィールド定義。
運用ルール自体（毎セッション最初に読む、完了の判定基準など）は `CLAUDE.md` 側の短い手順を参照。

## tasks.json のフィールド

各タスクは以下のフィールドを持つオブジェクト:

| フィールド     | 内容                                                           |
| -------------- | -------------------------------------------------------------- |
| `id`           | `T-001` のような通し番号                                       |
| `task`         | タスクの内容（背景・理由が分かるように具体的に書く）           |
| `status`       | `todo` / `doing` / `done`                                      |
| `difficulty`   | `haiku` / `sonnet` / `opus`（実行に使うモデルの目安。下記）    |
| `passes`       | 完了条件を満たしたか（`boolean`）                              |
| `evidence`     | 完了の証拠（コミットハッシュ、テスト件数、生成物へのパスなど） |
| `dependencies` | 先に完了している必要がある他タスクの `id` 配列                 |

## difficulty（タスクの難易度）

タスクごとに必要な判断の重さを3段階で表す。**モデル名だが「どのモデルを使うか」ではなく
「どれだけの判断を要するか」を表すラベル**として扱い、タスクを登録した時点で付ける。
難易度に応じて実行モデルを切り替える運用を想定している。

| 値       | 基準                                                                                                                                             | 例                                                   |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------- |
| `haiku`  | 機械的な作業。判断がほぼ不要で正解が1つに定まる（ファイルの移動、名前の一括置換、ドキュメントへの追記）                                          | T-047（`types.ts`からブランド型を1ファイル抜き出す） |
| `sonnet` | 通常の実装。設計判断はあるが局所的で、既存の方針・前例に沿えば決まる。複数ファイルにまたがる分割やテスト追加を含む                               | T-044〜T-046（責務ごとのファイル分割）、T-041        |
| `opus`   | 方針・設計そのものの判断が必要。既存の原則との衝突を解く、選択肢のトレードオフを比較する、並行性やエラー方針など間違えても気づきにくいものを扱う | T-038（`config/`の運用方針決め）、T-042（並列化）    |

運用ルール:

- 迷ったら1段上を選ぶ（判断を要するタスクを機械的に処理させるほうが、その逆より事故が大きい）
- 「作業量が多い」ことは難易度を上げる理由にならない。**判断の質**だけで決める
- 着手してみて想定より判断が必要だと分かったら、`difficulty` を上げてから再開する
- 完了済み（`done`）のタスクには遡って付けない。実行前の見積もりに使う値なので、
  完了後は `evidence` が実績を語る

## difficulty に応じたモデルの切り替え方

セッションを実行しているモデル（Claude Code のメインループ）は**自分自身のモデルを途中で
変えられない**。そのため切り替えは、`haiku`/`sonnet` のタスクを**そのモデル指定のサブ
エージェントに委譲する**ことで行う（ユーザー判断、2026-09-06）。

- `haiku` / `sonnet` → Agentツールで `model` を指定して委譲する
- `opus` → メインセッションがそのまま実行する（親がOpusなので委譲しても利得が無く、
  コールドスタートの分だけ損になる）
- **委譲しないケース**: ユーザーへの確認が必要なタスク（サブエージェントはユーザーに
  質問できない）と、会話中の文脈に依存するタスク。方針決めはメインで済ませてから、
  決まった作業だけを委譲する
- サブエージェントは**まっさらな文脈で起動する**ため、`tasks.json` の `task` 本文だけで
  作業が完結するように書く（対象ファイル・完了条件・`pnpm check` を通すことを明記する）
- 委譲したタスクも、完了報告をそのまま信用せず `pnpm check` の結果で受け入れを判定し、
  `evidence` はメイン側で書く

## progress.md の構成

以下の4セクションで構成する:

- **完了したこと**: 何を、なぜ、どう検証したか（コミットハッシュ・テスト件数を添える）。
  **このセッション分のみ**を書き、過去セッション分はアーカイブへ移す（下記）
- **次にやること**: 未着手タスクの一覧（`tasks.json`の`id`を添える）
- **未解決**: 判断が必要で保留中の事項
- **注意**: 誤解しやすい前提・外部リソースの状態など、次回セッションで踏み外しやすい点

## 良いevidenceの書き方

「完了しました」という宣言だけでは合格にしない。次のような、後から検証可能な形で残す:

- コミットハッシュ（`commit e59c410` のように）
- `pnpm check` の通過件数（テスト件数が変わっていれば増減が分かる）
- 生成物や検証ログへの具体的な参照

**書かないこと**（T-030）: 設計変更の物語、検討して撤回した案、実機検証の手順の詳細、
変更したファイルの列挙。これらは後から誰も参照しないわりに `tasks.json` を肥大化させ、
毎セッション冒頭に全件読む運用のコストを押し上げる。判断の経緯を残したい場合は、
要件に関わるものは `docs/requirements-grilling.md`、設計に関わるものは
`docs/architecture.md` か下記のアーカイブへ書く。目安として1タスクのevidenceは
**3行以内**に収める。

## 肥大化したときのアーカイブ

`tasks.json` と `progress.md` は毎セッション冒頭に読むファイルなので、増え続けさせない:

- `tasks.json` の完了タスクの詳細な記録 → `docs/history/tasks-archive.md`
  （evidenceは「コミットハッシュ・テスト件数・アーカイブへの参照」に置き換える）
- `progress.md` の過去セッションの「完了したこと」 → `docs/history/progress-archive.md`

アーカイブは当時の記述をそのまま移すだけにし、後から書き換えない（当時のファイル名・型名が
現在と違っていても履歴としてそのまま残す）。

### いつ移すか（トリガー）

- セッション開始時に `tasks.json` の `status: done` が **10件以上**あったら、作業を始める前に
  アーカイブする
- 件数が10件未満でも `tasks.json` が **30KB を超えていたら**、`done` を減らせないか検討する
  （evidenceが肥大化しているだけの場合はevidenceの圧縮、件数自体が多い場合はアーカイブを検討）

### 何を移すか

- `done` のタスクは**全件**アーカイブする（直近セッションで完了した分も含む）。直近セッションの
  記録は `progress.md` の「完了したこと」が担うため、`tasks.json` 側に別途残す必要はない
- タスクIDの通し番号は再利用せず、常に続きから採番する

### `dependencies` の扱い

- アーカイブ済みタスクのIDを指す `dependencies` は**そのまま残す**（書き換えない）
- **`tasks.json` に存在しないタスクIDは「アーカイブ済み＝完了」とみなす**。依存解決の際は
  `tasks.json` の `id` 一覧に無い `dependencies` エントリを完了済みとして扱ってよい
