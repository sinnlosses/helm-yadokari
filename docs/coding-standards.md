# コーディング規約の詳細

`CLAUDE.md`「コーディング規約・レビュー方針」にルールの一覧がある。**ここにはその理由と例外**
だけを書く（ルール本体はCLAUDE.md側が正典で、二重に書かない）。`/code-review` のStandards軸は
この2つを合わせて評価軸にする。

配置・分割・型の置き場所といった**構成**の規約は `docs/architecture.md` が正典。

## 関数の並び順

ファイル内で「外から使うもの → その内部で使うもの」の順に並べ、`export` された関数を上に、
そこからしか呼ばれない非公開関数を下に置く。非公開関数同士は呼ばれる順に並べる。

読む人がファイルを開いて最初に目にするのが、そのファイルの公開インターフェースになるようにする
ため。目次を別に置かなくてもファイルの先頭が目次として働く。

### テストのためだけの `export` はしない

非公開関数はエクスポートされた関数の振る舞いを通して検証する。テストのためにexportすると、
「このファイルの公開インターフェース」がテストの都合で膨らみ、上の並び順の意味も崩れる。

- **例外は `src/lib/env.ts` の個別パーサ群**。環境変数ごとの検証を`loadEnvConfig()`経由では
  なく直接テストするために`export`している（1つの環境変数の検証を確かめるのに、他の環境変数を
  すべて揃えた`EnvConfig`を組み立てる必要が出てしまうため）

## `as` キャストを使わない

ブランド型（`ProjectId`・`BranchName`等）の生成は`toProjectId`のようなfactory関数に封じ込め、
それ以外で`as`を使わない。factoryに集めることで、値の検証（http(s)かどうか、空文字でないか）を
通っていないブランド型が存在しえなくなる。どのブランド型を新設するかの基準は
`docs/architecture.md`「ブランド型にするのは『同じ`string`の別物と取り違えうる識別子』」参照。

## 変数は基本 `const`

再代入が必要に見える場合はまず、値を返す関数に切り出せないか（`reduce`、早期return付きの
ヘルパー関数など）を検討する。ループカウンタや、`try`/`catch`で外側のスコープに結果を持ち出す
必要があるなど`let`が自然な場合はその限りではない。

不変性はローカル変数だけでなくコレクションにも適用する（`ReadonlyMap`・`readonly`フィールド）。
引数として渡した入れ物が呼び出し先で書き変わる契約にしない理由は
`docs/architecture.md`「`ValuesYamlDraft`は受け取って返す」参照。

## エラーハンドリング

- HTTPエラーの判定は `src/utils/http.ts` の既存ユーティリティ（`isFatalError`等）を使う。
  ステータスコードの直書きを散らさないため
- 401 / 5xx / ネットワーク障害は `FatalError` を投げて即時終了、それ以外のエラーは該当chart
  リポジトリを `ERROR` としてログ記録し処理継続する（README「エラーハンドリング」参照）
- **`src/steps/` 配下に `try`/`catch` を書かない**。理由と、この規約の対象外になる箇所は
  `docs/architecture.md`「エラー方針は『fatalは例外・それ以外は戻り値』の2チャネル」参照

## 環境変数

すべて `src/lib/env.ts` で管理し、読み取りは `loadEnvConfig()` を通す。モジュールの
トップレベルでは `process.env` に触れない。トップレベルで読んでいた頃に何が起きたかは
`docs/architecture.md`「環境変数はモジュールのトップレベルではなく`loadEnvConfig()`で読む」参照。

## コメント

**コードから読み取れないことだけ**を書く。型名・フィールド名・関数名の言い換え
（`FileUpdate` に「1ファイル分の更新内容」など）は書かない。書く場合も**原則1〜2文**に収める。

それを超える背景・理由・経緯は正典に置いて二重管理しない:

| 書きたいこと   | 置き場所               |
| -------------- | ---------------------- |
| 設計判断・経緯 | `docs/architecture.md` |
| ドメイン用語   | `docs/glossary.md`     |
| 要件           | `docs/requirements.md` |

コメントとして残す価値があるのは次の2つ:

- **外部との対応関係**: どのYAMLキー由来か、GitLab APIのどの挙動に依存するか
- **非自明な前提・制約**: その順序でなければならない理由など

## タスク番号を書かない

コード・ドキュメントにタスク番号（`develop/tasks.json` の `id`。`T-` + 3桁の連番）を書かない。
変更の経緯は `develop/tasks.json` と `docs/history/` 側に持たせ、コードやドキュメントには
「現在どうなっているか」と「なぜそうなっているか」だけを書く。

タスク番号はアーカイブされると意味を失う一方、コード側の記述は残り続けるため、参照先が消えた
死んだ識別子になる。この規約は `grep -rE "T-[0-9]{3}"` が `develop/` / `docs/history/` 以外で
0件になることで機械的に確認できる。
