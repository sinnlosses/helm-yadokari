## 目的・背景
新しい chart リポジトリを `config/` に登録するとき、`registry.yaml`・`versions.yaml`・`locations.yaml` を手で書いている。書く中身は `values.yaml` のYAMLアンカー（`&myAppVersion` など）と chart のディレクトリ構成からほぼ決まるのに、アンカー名・`valuesPath`・`helm[]` の網羅を人が写していて、写し漏れは `pnpm lint` まで分からない。これを Claude Code のスキルにして、手元に clone した chart リポジトリから設定を下書きさせる。

いまこのリポジトリにはプロジェクト単位のスキル（`.claude/skills/`）が1つも無い。`CLAUDE.md` の「導入済みスキル」節は、スキルがすべてユーザー単位（`~/.claude/skills/`、claude-skills リポジトリ）にある前提で書かれている。

設定の形式の正典は `docs/requirements.md` 4.4節（`sed -n '/^### 4.4 アプリの登録・設定/,/^#\{2,4\} /p' docs/requirements.md`）。

## 決まっていること（蒸し返さない）

- 2026-09-30 ユーザー決定: 新しい chart ディレクトリ一式の生成と、既存の chart ディレクトリへの設定ユニット・app の追加の両方を扱う
- スキルは設定ファイルを書くところまでで、コミット・MR の作成はしない。書いたあとに `pnpm lint:validate-config` を通すところまでをスキルの手順に含める

## 解くべき論点
- アンカーと app の対応づけ: `values.yaml` のアンカーのうち、どれがイメージタグ（`apps`）で、どれが Helm の向き先ブランチ（`helm[]`）か。app 名（`registry.yaml` の `projectName`）とどう結びつけるか。名前からの推測をユーザーに確認させる流れにするか
- 設定ユニットの切り方: chart のディレクトリ構成（例 `charts/<tenant>/<client>/values.yaml`）から `unitPath` の候補をどう出し、どこでユーザーに決めさせるか
- `tagFormat`・`branchToSync`・`branchRef` の初期値: `values.yaml` の今の値から推測するか、必ず尋ねるか
- 既存の chart ディレクトリへの追加で、既存の `registry.yaml` の `appSpecs[]` とどう突き合わせるか（名前の重複・既存 app の再利用）

- `CLAUDE.md` の「導入済みスキル」節と、必要なら `README.md` に、プロジェクト単位のスキルがあることと使い方の入口が書かれている
- `pnpm check` が通る

## 注意
- スキルの書き方は `skill-creator` スキルを参照してよい。description にはトリガーになる言い回し（「chart を登録したい」「config を生成したい」など）を入れる
- `CLAUDE.md` の記述どおり、ユーザー単位の同名スキルはプロジェクト単位より優先される。ユーザー単位のスキルと名前が重ならないようにする
- 検証は、`config.example/` をリポジトリ内の一時ディレクトリに複製して `npx tsx scripts/lint/validate-config.ts <そのディレクトリ>` で試せる（リポジトリの外のパスは弾かれる）
