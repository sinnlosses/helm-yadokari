## 目的・背景
新しい chart リポジトリを `config/` に登録するとき、`registry.yaml`・`versions.yaml`・`locations.yaml` を手で書いている。書く中身は `values.yaml` のYAMLアンカー（`&myAppVersion` など）と chart のディレクトリ構成からほぼ決まるのに、アンカー名・`valuesPath`・`helm[]` の網羅を人が写していて、写し漏れは `pnpm lint` まで分からない。これを Claude Code のスキルにして、手元に clone した chart リポジトリから設定を下書きさせる。

いまこのリポジトリにはプロジェクト単位のスキル（`.claude/skills/`）が1つも無い。`CLAUDE.md` の「導入済みスキル」節は、スキルがすべてユーザー単位（`~/.claude/skills/`、claude-skills リポジトリ）にある前提で書かれている。

設定の形式の正典は `docs/requirements.md` 4.4節（`sed -n '/^### 4.4 アプリの登録・設定/,/^#\{2,4\} /p' docs/requirements.md`）。

## 解くべき論点
- アンカーと app の対応づけ: `values.yaml` のアンカーのうち、どれがイメージタグ（`apps`）で、どれが Helm の向き先ブランチ（`helm[]`）か。app 名（`registry.yaml` の `projectName`）とどう結びつけるか。名前からの推測をユーザーに確認させる流れにするか
- 設定ユニットの切り方: chart のディレクトリ構成（例 `charts/<tenant>/<client>/values.yaml`）から `unitPath` の候補をどう出し、どこでユーザーに決めさせるか
- `tagFormat`・`branchToSync`・`branchRef` の初期値: `values.yaml` の今の値から推測するか、必ず尋ねるか
- 既存の chart ディレクトリへの追加で、既存の `registry.yaml` の `appSpecs[]` とどう突き合わせるか（名前の重複・既存 app の再利用）

### 論点への答え（SKILL.md の手順にそのまま落とす）

**論点1 アンカーと app の対応づけ** — 案: 名前と今の値の両方で分類し、表にして必ず確認させる。
- 対象は clone 内の `values*.yaml`（`Chart.yaml` があるディレクトリ配下。無ければ clone 全体、`.git/`・`node_modules/` は除く）の、**スカラー値に付いた**アンカー（`&name value`）。マッピング・シーケンスに付いたアンカーは本体が書き換えられない（`src/lib/helm.ts` の `non_scalar`）ので候補から外し、外したことを表に出す
- 分類の根拠は2つ。(a) 今の値: 8桁の数字と6桁の数字を含む（`{date}`/`{time}` に読める）ならイメージタグ、ブランチ名らしい値（`main`・`develop`・`release/...` など）なら向き先ブランチ。(b) 名前: `Version`・`Tag` を含むならイメージタグ、`Branch`・`TargetBranch`・`Ref` を含むなら向き先ブランチ。**(a)(b) が一致したものだけ分類済み**とし、食い違う・どちらにも当たらないものは「不明」に置く（例: スモークの `&helmVersion develop` は名前はタグ、値はブランチなので不明。登録しない選択肢も示す）
- app 名（`projectName`）の候補は、イメージタグのアンカー名から `Version`/`Tag` とその後ろ（`Extra` など）を落として kebab-case にしたもの（`myAppVersion`・`myAppVersionExtra` → `my-app`）。同じ候補名に落ちたアンカーは1つの app の複数書き込み先（`apps.<app>[]` の複数要素）にまとめて提案する
- ユーザーに見せるのは「アンカー / valuesPath / 今の値 / 分類 / app 名の候補」の表1つ。app 名はソースリポジトリ名と揃えるのが既定（`config/` の実例がそうしている）なので、候補をそのまま使うか、実際のリポジトリ名を尋ねる。**推測だけで書き出さず、この表の確認を必ず挟む**（写し漏れを防ぐのがスキルの目的で、推測の誤りは lint でも見つからない＝アンカーの実在は `--remote` でしか見ないため）

**論点2 設定ユニットの切り方** — 案: 「values ファイルを持つディレクトリ1つ＝設定ユニット1つ」を候補にし、`unitPath` はそのパスから提案して確認させる。
- 同じディレクトリの複数の values ファイル（`values.yaml` と `values-extra.yaml`）は同じユニットにまとめる（`config.example/.../client-a` と `config/.../tenant2/client1` がこの形）
- `unitPath` の候補は、そのディレクトリの clone 内パスから先頭の `charts/` を落とした残り。1〜2セグメントならそのまま、3セグメント以上なら末尾2セグメントを候補にする（深さ3以上は設定エラーのため）。候補が実例のように chart 側と違う名前でよい（固定ブランチ `feature/yadokari/<unitPath>` の名前になるだけ）ことを添える
- 提示は論点1の表の直後に「ユニット候補 / 含む values ファイル / unitPath 候補」の表1つで行い、ユーザーはここで unitPath の変更・ユニットの統合・対象外にするユニットの除外を決める。スキル側で次を事前に検査して表に注記する: 深さが1〜2か、候補同士・既存ユニットとの**入れ子**・重複が無いか、ref に使えない文字（空白・`..`・`~^:?*[\` など）を含まないか
- 1ユニットの `helm[]` は、そのユニットの全 app の全 `valuesPath` をカバーする必要がある。ユニット内の values ファイルに向き先ブランチのアンカーが見つからないものがあれば、書き出す前にその旨を出して決めさせる（そのまま書くと lint で落ちる）

**論点3 `tagFormat`・`branchToSync`・`branchRef` の初期値** — 案: 今の値から推測して**既定値として提示**し、確認を必ず取る（黙って採用はしない、白紙で尋ねもしない）。
- `tagFormat`: 同じ `projectId` がどこかの `config/*/registry.yaml` に既にあればその値を使う（食い違いは設定エラーなので推測より優先）。無ければ今のタグ値の8桁数字を `{date}`、6桁数字を `{time}`、残りのうち区切り以外の部分を `{branch}` に置き換えて提案する（`main-build-at-20260101-000000` → `{branch}-build-at-{date}-{time}`）。8桁・6桁が見つからない値からは推測せず尋ねる。提案した形式が `{branch}`/`{date}`/`{time}` を1回ずつ含むことをその場で確かめる
- `branchToSync`: 上で推した `tagFormat` でタグ値の `{branch}` 部分を取り出して提案する。ただし `/` が `-` に潰れている可能性（`release-x` は `release/x` かもしれない）を必ず添えて確認させる
- `branchRef`: そのユニットの向き先ブランチのアンカーの今の値。同じ値を書けば差分が出ない（4.4節）ので、既定として安全。ユニット内のアンカー同士で今の値が違う場合は、本体が全部を同じ `branchRef` に揃えることを伝えて1つ選ばせる
- `registry.yaml` 側のファイルから分からない値は尋ねる: `chartToUpdate.projectId`（GitLab は数値。GitHub の `"owner/repo"` は clone の `git remote get-url origin` から候補を出してよい。API は呼ばない）、`group.groupId`/`groupName`（`groupName` は remote URL のパスから候補可）、`accessTokenEnv`（`^ACCESS_TOKEN_[A-Z0-9_]+$`。同じグループの既存 chart ディレクトリがあればその値を候補にする）、`appSpecs[].projectId`。`chartToUpdate.projectName` と `config/` のディレクトリ名は clone のディレクトリ名（または remote のリポジトリ名）を候補に、`mrTargetBranch` は `git -C <clone> symbolic-ref --short refs/remotes/origin/HEAD` の結果（取れなければ尋ねる）を候補にする

**論点4 既存 chart ディレクトリへの追加** — 案: 既存の `registry.yaml` を台帳として先に読み、そこに合わせる。
- どの既存ディレクトリか: 全 `config/*/registry.yaml` の `chartToUpdate.projectName` が clone の名前と一致するもの（見つからなければ新規、候補が曖昧なら尋ねる。`projectId` はユーザーに聞いた値で最終確認する）。見つかったら「新規生成」ではなく「追加」の手順に切り替えることを告げる
- 既存 app の再利用: 論点1で出した app 名の候補が既存の `appSpecs[].projectName` と一致したら、その app を再利用する提案にする（`projectId`・`tagFormat` は既存値を使い、尋ねない）。一致しない新しい app だけ `appSpecs[]` に追記する
- 名前の重複: 新しい app の `projectName` が既存と重なるのに別のソースリポジトリだと言われたら、別名を決めさせる（重複は設定エラー）。新しい app の `projectId` が同じ `registry.yaml` に別名で既にあれば、既存名に寄せる（`projectId` 重複も設定エラー）
- 他の chart ディレクトリ: 新しい app の `projectId` が別の `config/*/registry.yaml` にもあれば、その `tagFormat` を使い、`accessTokenEnv` が違うなら「1つの projectId は1つのトークンにしか結びつけられない」制約で落ちることを書き出す前に伝える
- 既存ユニットへの app 追加も扱う: 追加先ユニットの `versions.yaml` の `branchToSync` と `locations.yaml` の `apps` の**両方**にキーを足し（キー集合の一致が必要）、新しい `valuesPath` があれば `helm[]` にも足す。既存の書き込み先（`valuesPath`+`anchor`）と重なるアンカーは候補から外す
- 既存ファイルは丸ごと書き直さず、足す行だけを編集する（既存のコメントを消さない）
