## 背景

T-263 で `registry.yaml` トップレベルに `group: <グループのフルパス>` を足し、
`validate-config --remote` がプロジェクトの所属を照合するようにした。しかし**特定にグループ名
（パス）を使っている点が誤り**。名前は変わるが ID は変わらない。

これはこのリポジトリの既存の規約に反している。`chartToUpdate` と `appSpecs[]` は
`projectId`（特定）＋ `projectName`（ラベル）の形を取り、`docs/glossary.md` にも
「**`projectName`をキーに入れない**: `projectId`と1:1のラベルで、同一性の判定には効かないため」
と明記されている。

いまの実装（T-263、コミット 5fa6f8b）:

- `src/domain/brand.ts` の `GroupPath` / `toGroupPath()`（セグメントを `/` でつないだ形式を検証）
- `src/lib/config/schema.ts` の `GroupPathSchema` と `RegistryYamlSchema.group`
- `src/domain/types.ts` の `ConfigUnit.groupPath`、`src/lib/config/load-config-unit.ts` の
  `ChartRepoScope.groupPath`
- `src/lib/gitlab/api.ts` の `getProjectGroupPath()`（`Projects.show` の `namespace.full_path` を返す）
- `scripts/lint/remote-existence/remote-cache.ts` の `lookupProjectGroupPath`（projectId単位でキャッシュ）
- `scripts/lint/remote-existence/remote-existence.ts` の `describeProjectProblems()` と
  `isWithinGroup()`（セグメント単位の前方一致）

調べて分かっていること:

- `Groups.show(groupId)` は `ExpandedGroupSchema` を返し `id` と `full_path` を持つ
  （gitbeaker 43.8.0）。`scripts/smoke/provision-group.ts:179` に `Groups.show()` を使う前例がある
- `Projects.show` が返す `namespace` は `id`・`full_path`・`parent_id` を持つ。`namespace.id` の
  一致だけではサブグループ配下かどうかを判定できない（`parent_id` は1階層ぶん）
- したがって **`groupId` から `full_path` を registry.yaml 単位で1回だけ引き、いまのセグメント
  単位の前方一致をそのまま使う**のが素直。projectId ごとの API 呼び出しは増えない

## 解くべき論点

- **`GroupId` のブランド型をどうするか**。`ProjectId` は GitLab の数値と GitHub の `owner/repo` を
  兼ねるため形式検証なしの文字列ブランド。グループは GitLab 専用なので数値のみに絞れる。
  `accessTokenEnv`（`toAccessTokenEnvName()`）のように factory で検証するか、`ProjectId` に
  倣って素通しにするかを決め、結論を型の JSDoc に残す。`GroupPath` は `Groups.show` が返す
  `full_path` を表す型として**残す**（YAMLから消えるだけで、照合には引き続き要る）
- **`groupId` → `full_path` の解決をどこに置くか**。`RemoteCache`（`remote-cache.ts`）は
  いま projectId 単位のキャッシュしか持たない。groupId 単位の解決を同じ `cacheByArgs` で
  足すか、`validate-config.ts` 側で registry.yaml ごとに1回引いて渡すかを決める。
  **projectId ごとの API 呼び出しを増やさないこと**
- **`groupId` が実在しない・トークンで参照できないときの扱い**。プロジェクトの所属照合が
  そもそも成立しないので、専用の文言で報告したうえでその registry.yaml 配下の所属照合を
  どう畳むか（実在チェックの他の項目は続けるか）を決める
- **`groupName` のズレの文言**。所属違い・不在と取り違えられない言い回しにする
- **`ConfigUnit` に何を載せるか**。`groupPath` を `groupId` + `groupName` に置き換えるのか、
  型の置き場所は `docs/architecture.md`「型の置き場所」に従う
