## 目的・背景
`src/steps/resolve-tags/sub-steps/resolve-latest-tag.ts` の `resolveLatestTag` は、`adapter.listTags` で
プロジェクトのタグを**全件**取り、`getBranchHeadSha` で得た HEAD のコミットを指すものだけを
`resolveTrackedHeadTagNames` で残している。取得の実体は次のとおり全ページを辿る。

- GitLab: `src/lib/gitlab/api.ts` の `listTags` が `gitlab.Tags.all(projectId)`（perPage 未指定なので
  GitLab 既定の20件/ページで全ページ）
- GitHub: `src/lib/github/api.ts` の `listTags` が `github.paginate(repos.listTags, { per_page: PER_PAGE })`

このツール自身が追跡ブランチの HEAD が進むたびにタグを作るので、タグは単調に増える。長期運用で
1アプリあたりのリクエスト数・所要時間・レート制限（GitHub は 5000 req/h）への影響が際限なく伸びる。
実際に要るのは「HEAD のコミットを指すタグ」だけなので、全件取得をやめたい。

`listTags` は `src/lib/platform/adapter.ts`（`PlatformAdapter`）・`token-routed-adapter.ts`・
`cached-reads.ts`（`createTag` でキャッシュを無効化している）・各 `adapter.ts` にも現れる。

## 決まっていること（蒸し返さない）
- 目的は「HEAD を指すタグを見つける」ことに必要な分だけを取ることで、タグの選び方
  （HEAD を指し、`branchToSync` と `tagFormat` でパースできるもの。複数あれば打刻日時が最新のもの）は変えない
- 全件取得をやめられないプラットフォームがあるなら、その理由を残したうえで、そのプラットフォームだけ現状維持でよい

## 解くべき論点
- GitLab で「あるコミットを指すタグ」を直接引く手段（例: コミットの refs を `type=tag` で引く API）が使えるか、
  権限・ページング・annotated tag の扱いを含めて確かめる
- GitHub で同じことをする手段（REST の matching-refs はタグ名の前方一致しかできず、`tagFormat` によっては
  `{branch}` が先頭に来ない。GraphQL を足すかどうか）と、その費用
- `PlatformAdapter` のインターフェースをどう変えるか（`listTags` を置き換えるか、別の関数を足すか）と、
  `cached-reads.ts` のキャッシュ無効化・`remote-existence` など `listTags` の他の利用箇所への影響
