## 目的・背景
`src/steps/resolve-tags/sub-steps/resolve-latest-tag.ts` の `resolveLatestTag` は、`adapter.listTags` で
プロジェクトのタグを**全件**取り、`getBranchHeadSha` で得た HEAD のコミットを指すものだけを
`resolveTrackedHeadTagNames` で残している。取得の実体は次のとおり全ページを辿る。

- GitLab: `src/lib/gitlab/api.ts` の `listTags` が `gitlab.Tags.all(projectId)`（perPage 未指定なので
  GitLab 既定の20件/ページで全ページ）
- GitHub: `src/lib/github/api.ts` の `listTags` が `github.paginate(repos.listTags, { per_page: PER_PAGE })`

このツール自身が追跡ブランチの HEAD が進むたびにタグを作るので、タグは単調に増える。長期運用で
1アプリあたりのリクエスト数・所要時間・レート制限（GitHub は 5000 req/h）への影響が際限なく伸びる。
実際に要るのは「HEAD のコミットを指すタグ」だけなので、全件取得をやめたい。

`listTags` は `src/lib/platform/adapter.ts`（`PlatformAdapter`）・`token-routed-adapter.ts`・
`cached-reads.ts`（`createTag` でキャッシュを無効化している）・各 `adapter.ts` にも現れる。

## 決まっていること（蒸し返さない）
- 目的は「HEAD を指すタグを見つける」ことに必要な分だけを取ることで、タグの選び方
  （HEAD を指し、`branchToSync` と `tagFormat` でパースできるもの。複数あれば打刻日時が最新のもの）は変えない
- 全件取得をやめられないプラットフォームがあるなら、その理由を残したうえで、そのプラットフォームだけ現状維持でよい

## 解くべき論点
- GitLab で「あるコミットを指すタグ」を直接引く手段（例: コミットの refs を `type=tag` で引く API）が使えるか、
  権限・ページング・annotated tag の扱いを含めて確かめる
- GitHub で同じことをする手段（REST の matching-refs はタグ名の前方一致しかできず、`tagFormat` によっては
  `{branch}` が先頭に来ない。GraphQL を足すかどうか）と、その費用
- `PlatformAdapter` のインターフェースをどう変えるか（`listTags` を置き換えるか、別の関数を足すか）と、
  `cached-reads.ts` のキャッシュ無効化・`remote-existence` など `listTags` の他の利用箇所への影響

## やること

### 調べて分かったこと（前提の確認）
- 目的・背景のパス・関数名はすべて実物どおり（`resolveLatestTag` は `listTags` と `getBranchHeadSha` を

  1点だけ表現がずれている: `cached-reads.ts` は `listTags` を「`createTag` で無効化」しているのではなく、
  **そもそもキャッシュに載せていない**（JSDoc に「`listTags`は`createTag`で…変わるので載せられない」とある）。
  作業には影響しない
- `listTags` / `TagInfo` の利用箇所は本体パイプラインの `resolve-latest-tag.ts` だけ。`scripts/`
  （`remote-existence` を含む）からは呼ばれていない（grep で 0 件）ので、置き換えの影響は src の

### 論点1（GitLab）の結論: `GET /projects/:id/repository/commits/:sha/refs?type=tag` を使う
- gitbeaker 43.8.0 に `gitlab.Commits.allReferences(projectId, sha, { type: "tag", perPage })` がある
  （戻り値 `CommitReferenceSchema[]` = `{ type, name }` だけ。コミット SHA は返らない）。
  `RequestHelper.get()` 経由なので `Tags.all` と同じく Link ヘッダを辿って自動ページングする
- 公式ドキュメント（docs.gitlab.com/api/commits/ の "Get references a commit is pushed to"）と
  GitLab 本体の実装（`lib/api/commits.rb`）で確かめた要点:
  - 実装は `Gitlab::Repositories::ContainingCommitFinder` で、**「そのコミットを指すタグ」ではなく
    「そのコミットを含む（祖先に持つ）タグ」**を返す（`git tag --contains` 相当）。HEAD の子孫の
    コミットに付いたタグ（HEAD から分岐した別ブランチのタグ、追跡ブランチを巻き戻した場合の
    旧タグ）も混ざる。よって**このエンドポイントだけでは「HEAD を指す」の判定はできず、候補の
    検証が要る**
  - 権限は `authorize_read_code!`（リポジトリの読み取り）。`Tags.all` と同じ権限で足り、
    トークンのスコープ（`read_api`）の追加は要らない
  - ページングは `page`/`per_page`（最大100）。`without_count` なので総数ヘッダは無いが next リンクは出る
  - annotated tag は `--contains` がタグを peel して判定するので、指す先のコミットで扱われる。
    検証に使う `Tags.show` の `commit.id` も peel 済みのコミット SHA（現行の `Tags.all` の
    `tag.commit.id` と同じ値）
- 検証の手順: refs で得たタグ名を**まず呼び出し側の述語（`parseTag` 可能か）で絞り**、残った候補
  だけを `gitlab.Tags.show(projectId, name)` で引いて `commit.id === sha` のものを残す。述語を先に
  当てるのは、追跡ブランチの HEAD から分岐した別ブランチに大量のタグが付いている場合
  （例: 長く動いていない `main` を追い、`develop` 側で毎回タグが増える）に、その全件を
  `Tags.show` で引くと全件取得より悪くなるため。述語を通るのは実質「このブランチ名で
  このツールが打ったタグ」だけで、通常 0〜1 件（巻き戻しがあった場合のみ数件）
- `Tags.show` が 404（refs を引いた直後に消された）なら候補から外す（既存の `withNotFoundFallback`）

### 論点2（GitHub）の結論: 全件取得を維持し、理由を JSDoc に残す
- REST にはコミットからタグを引く手段が無い（`commits/{sha}/branches-where-head` はブランチのみ、
  `git/matching-refs/tags/<prefix>` はタグ名の前方一致だけで、`tagFormat` の先頭が `{branch}` でも
  「そのブランチの全タグ」になり件数は同じように単調に増える）
- GraphQL にも Commit から紐づくタグを引くフィールドは無い。`Repository.refs(refPrefix: "refs/tags/",
  orderBy: {field: TAG_COMMIT_DATE, direction: DESC})` で先頭から読み、HEAD のコミット日時より
  古くなったら打ち切る案はあるが、コミット日時は rebase・時計ずれで単調ではないため打ち切りの
  正しさを保証できない（取りこぼすと既存タグがあるのに新規タグを作る＝選び方が変わる）。加えて
  GraphQL を足すと `lib/github/errors.ts` のエラー分類（GraphQL は 200 + `errors` で返る）・リトライ・
  テストの偽装を別系統で持つことになり、費用に見合わない
- よって GitHub は現状どおり `paginate(repos.listTags, { per_page: 100 })` で全件取り、その中で
  絞る。**理由は `src/lib/github/api.ts` の新関数の JSDoc に書く**（完了条件2行目）

### 論点3（インターフェース）の結論: `listTags` を `listTagsAtCommit` に置き換える
- `PlatformAdapter.listTags` を削除し、次を足す（`src/lib/platform/adapter.ts`）:
  ```ts
  /**
   * `commitSha`を指すタグのうち、`isCandidate`を満たすものの名前を返す。
   * `isCandidate`はコミットの照合より前に当てる（照合に1件1リクエスト要るプラットフォームがあるため）
   */
  readonly listTagsAtCommit: (
    projectId: ProjectId,
    commitSha: CommitSha,
    isCandidate: (name: TagName) => boolean,
  ) => Promise<TagName[]>
  ```
  述語を引数にするのは、「どのタグ名が追跡ブランチ由来か」（`parseTag`＋`tagFormat`）の判断を
  `steps/` に残したまま、GitLab 側で `Tags.show` の回数を候補だけに抑えるため（`lib/` に
  `tagFormat` を持ち込まない。原則2）。戻り値は `TagInfo[]` ではなく `TagName[]`（SHA は全件
  `commitSha` と同じなので持たせない）
- 別関数を足して `listTags` を残す案は採らない。本体パイプライン・`scripts/` のどちらにも他の利用者が
  いない（上記 grep）ため、残すと使われない関数になる
- `cached-reads.ts`: 新関数も `createTag` で結果が変わるのでキャッシュには載せない。JSDoc の
  「`listTags`は`createTag`で」を「`listTagsAtCommit`は`createTag`で」に置き換えるだけ
- `remote-existence`（`scripts/lint/remote-existence/`）は `listTags` を使っていないので影響なし
