## 目的・背景
`config/` のYAMLに知らないキーを書くと、黙って無視されて検証（`pnpm lint` の `scripts/lint/validate-config.ts`）を通ってしまう。`src/lib/config/schema.ts` のスキーマがどれも `z.object`（知らないキーを捨てる zod の既定）で組まれているため。対象は `RegistryYamlSchema`（`group`・`chartToUpdate`・`AppSpecSchema` を含む）、`VersionsYamlSchema`、`LocationsYamlSchema`、`AnchorLocationSchema`。

2026-09-30 に `config.example/` を複製して壊して試したところ、`versions.yaml` に `extra: 1` を足しても `config OK` になった。設定ユニットが `versions.yaml` と `locations.yaml` に分かれたので、古い `config.yaml` の癖で `helm:` や `apps:` を `versions.yaml` に書くような「キーを書くファイルを間違える」誤りが起きやすくなっている。これも素通りする。

## 決まっていること（蒸し返さない）
- 知らないキーは設定エラーにする（`registry.yaml`・`versions.yaml`・`locations.yaml` の全階層）
- エラーメッセージからは、どのファイルのどのキーが知らないキーかが分かるようにする

## 解くべき論点
なし

## やること

前提の確認（2026-09-30 時点の実物）: zod は `^4.4.3`（`z.strictObject` が使える）。`src/lib/config/schema.ts` の `z.object(` は7箇所（`AnchorLocationSchema`・`AppSpecSchema`・`GroupSchema`・`RegistryYamlSchema` 本体・その中の `chartToUpdate`・`VersionsYamlSchema`・`LocationsYamlSchema`）で、これで全階層。`appMapSchema` は `z.record`（キー＝app名）なので対象外。エラーは `src/utils/yaml.ts` の `parseYamlFile()` が `${filePath} の形式が不正です: ${result.error.message}` で投げ、zod 4 の `error.message` は issue の JSON（`code: "unrecognized_keys"`・`keys`・`path`）を含むため、ファイル名と知らないキー・階層は既に出る。よって `yaml.ts` は変えない。`config/` 実物・`config.example/`・スモークのフィクスチャ生成（`scripts/smoke/group-fixture-content.ts` の `buildRegistryYamlContent` / `buildVersionsYamlContent` / `buildLocationsYamlContent`）を読んだところ、知らないキーは無い（コメントはYAMLパーサが捨てる）。

1. `src/lib/config/schema.ts`: 上記7つの `z.object(` を `z.strictObject(` に置き換える。`GroupSchema` は第2引数に `{ error: ... }` を渡しているので、その形のまま引数を維持する。`AnchorLocationSchema` は `z.strictObject({...}).transform(...)` の順（transform 後は strict にできない）。あわせてファイル冒頭の `/** ... */` に「知らないキーは設定エラー（`z.strictObject`）」を1行足す（今の挙動の制約のため）。
2. `test/lib/config/schema.test.ts` に `describe("loadConfig（知らないキー）")` を足し、`useConfigDir()`・`registryYaml()`・`configUnitFiles()`（または `dir.writeConfigUnit()` に YAML 文字列を直接渡す）で正常な設定を書いたうえで1箇所だけ `extra: 1` を足すテストを、階層ごとに1件ずつ書く（`it.each` でまとめてよい）。各件は `expect(() => loadConfig(dir.path)).toThrow(...)` で、ファイル名（`registry.yaml` / `versions.yaml` / `locations.yaml`）と知らないキー名（`extra`）が両方メッセージに含まれることを確かめる。階層は、registry のトップレベル・`group`・`chartToUpdate`・`appSpecs[]` の要素、versions のトップレベル、locations のトップレベル・`helm[]` の要素・`apps.<app>[]` の要素。YAML文字列は既存のスキーマ検証テストと同じくその場で直接書く（`registryYaml()` は追加キーを出せないため、registry 側は出力文字列に `extra: 1` の行を差し込む）。
3. 同ファイルに「`versions.yaml` に `helm:` を書いたとき」のテストを足す（`versions` に `branchRef`・`branchToSync` に加えて `helm:` の配列を書き、`locations` は正常。メッセージに `versions.yaml` と `helm` が含まれることを確かめる）。
4. `docs/requirements.md` 4.4節: 「`versions.yaml`と`locations.yaml`は両方そろって初めて設定ユニットになり…」の箇条書きの近くに、「`registry.yaml`・`versions.yaml`・`locations.yaml` の全階層（`group`・`chartToUpdate`・`appSpecs[]`・`helm[]`・`apps.<app>[]` の要素を含む）で、知らないキーは設定エラーになる。書き間違いや、キーを書くファイルの取り違え（`versions.yaml` に `helm:` を書くなど）が黙って無視されないようにするため。エラーにはファイル名と知らないキーの名前・階層が出る。YAMLのコメントはキーではないので影響しない」を1項目追加する。`README.md` の「設定 > config/」章に同趣旨の記述を置くべき箇所があれば `grep` で確かめて追随する（無ければ触らない）。
5. 確認: `config/` と `config.example/` が `pnpm lint`（`scripts/lint/validate-config.ts`）を通ること。`config.example/` をリポジトリ内の一時ディレクトリに複製し、`versions.yaml` に `extra: 1` を足して `npx tsx scripts/lint/validate-config.ts <そのディレクトリ>` がエラーになることを見てから、複製を消す。最後に `pnpm check`。

## 完了条件
- 3種のファイルのどの階層（トップレベル、`group`・`chartToUpdate`・`appSpecs[]` の要素、`helm[]`・`apps` の書き込み先の要素）に知らないキーを書いても、`loadConfig()` が設定エラーになる。テストで確かめる
- `versions.yaml` に `helm:` を書いたとき（ファイルを取り違えた典型）のテストがある
- `docs/requirements.md` 4.4節に「知らないキーは設定エラー」が書かれている
- `config/` と `config.example/` が引き続き検証を通る（今あるファイルに知らないキーが紛れていたら、実物を見て直す）
- `pnpm check` が通る
