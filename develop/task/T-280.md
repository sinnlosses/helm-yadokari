## 目的・背景
`src/lib/helm.ts` の `setValueAtAnchor` は `parseDocument` → ノードの値を書き換え → `doc.toString()` で
**ファイル全体を再シリアライズ**している。その結果、アンカー1箇所の更新でも次の変化が MR の差分に混ざる
（yaml@2.9.0 で実測済み）。

- 4スペースのインデントが2スペースになる
- 80桁を超える文字列が折り返される
- 行末コメントの前の複数スペースが1つに詰まる
- flow 形式 `{a: 1}` が `{ a: 1 }` になる
- CRLF が LF になり、BOM が消える

JSDoc には「他の要素・インデント・アンカー記法自体はそのまま維持される」とあり、実際の挙動と食い違っている。
差分のノイズでレビューしづらくなり、人手の MR ともコンフリクトしやすい。

## 決まっていること（蒸し返さない）
- 書き換え後のファイルは、アンカーが付いたスカラーの値の部分以外、元の内容とバイト単位で一致させる
  （改行コード・BOM・インデント・コメント・他の値の書式を含む）
- アンカーの探し方・エラー（アンカーが無い、スカラーでない）の扱いは変えない

## 完了条件
- 上の「目的・背景」の各ケース（4スペースインデント、80桁超の文字列、コメント前の複数スペース、flow 形式、CRLF、BOM）を含む values.yaml で、書き換え後の差分がアンカーの値だけになることをテストで確かめる
- 元の値が引用符付き（`"..."`・`'...'`）・引用符なしのどちらでも、書き換え後に YAML として同じ値に読める
- `setValueAtAnchor` の JSDoc が実際の挙動と一致している
- `pnpm check` が通る

## 注意
- 新しい値に YAML で特別な意味を持つ文字が入る可能性（タグ名の形式は `tagFormat` 次第）を考え、引用符が要るときに壊れた YAML を書かないこと
- 空値・null のアンカー（`tag: &a` / `tag: &a ""`）の書き換えも壊さないこと（MR 本文の扱いは別タスク）
