## 目的・背景
`src/lib/helm.ts` の `setValueAtAnchor` は `parseDocument` → ノードの値を書き換え → `doc.toString()` で
**ファイル全体を再シリアライズ**している。その結果、アンカー1箇所の更新でも次の変化が MR の差分に混ざる
（yaml@2.9.0 で実測済み）。

- 4スペースのインデントが2スペースになる
- 80桁を超える文字列が折り返される
- 行末コメントの前の複数スペースが1つに詰まる
- flow 形式 `{a: 1}` が `{ a: 1 }` になる
- CRLF が LF になり、BOM が消える

JSDoc には「他の要素・インデント・アンカー記法自体はそのまま維持される」とあり、実際の挙動と食い違っている。
差分のノイズでレビューしづらくなり、人手の MR ともコンフリクトしやすい。

## 決まっていること（蒸し返さない）
- 書き換え後のファイルは、アンカーが付いたスカラーの値の部分以外、元の内容とバイト単位で一致させる
  （改行コード・BOM・インデント・コメント・他の値の書式を含む）
- アンカーの探し方・エラー（アンカーが無い、スカラーでない）の扱いは変えない

## 解くべき論点
なし

## やること
前提は実物で確認済み（`setValueAtAnchor` は `src/lib/helm.ts` にあり、`doc.toString()` で全体を再出力している。呼び出し元は `src/steps/build-plans/sub-steps/stage-image-tag-updates.ts:117` と `stage-helm-branch-ref-updates.ts:75` の2箇所で、シグネチャを変えないので触らない）。

方針: yaml の `Scalar.range`（`[値の開始, 値の終了, ノード終了]`、BOM・CRLF を含む元文字列上のオフセット）で、アンカー付きスカラーの値部分の文字列上の位置を特定し、その区間だけを差し替える。スクラッチで実測し、BOM・CRLF・行末コメント・`"..."`・`'...'`・引用符なし・数値 `2026`・空 `""` のいずれでも `yamlContent.slice(range[0], range[1])` が値そのもの（引用符込み）に一致することを確認済み。

1. `src/lib/helm.ts` の `setValueAtAnchor`（完了条件「差分がアンカーの値だけ」「JSDoc」）
   - `doc.toString()` をやめ、`lookup.node.range` から `yamlContent.slice(0, start) + 新しい値の表記 + yamlContent.slice(end)` を返す。`findAnchorNode` / エラー文言 / `AnchorLookup` は変えない（`range` は `Scalar` が持つので型の変更は不要。`range` が `undefined`/`null` になりうる型なら、無いときは内部不整合として例外を投げる）
   - 空値アンカー（`- &z` や `tag: &a`）は `range` が `[n, n, n]` の空区間になり、そのまま差すと `&znew` と繋がって壊れる。`range[0] === range[1]` のときは先頭に半角スペース1つを足して挿入する（注意欄「空値・null のアンカー」）。`tag: &a ""` は通常の `""` の置換として扱える
   - 新しい値の表記は非公開の小さな関数（例 `formatScalarLike(originalType, newValue)`）で作り、`setValueAtAnchor` の下に置く（関数は「外→内部」の順）:
     - 元が `QUOTE_DOUBLE` → `JSON.stringify(newValue)`（JSON の文字列は YAML の二重引用符と互換）
     - 元が `QUOTE_SINGLE` → 値に改行を含まなければ `'` + `newValue.replaceAll("'", "''")` + `'`、含むなら二重引用符にフォールバック
     - それ以外（引用符なし・空値・ブロックスカラー）→ `yaml` の `stringify(newValue, { lineWidth: 0 })` の末尾改行を除いたもの。これで `2027` のような数値に見える値・`true`・`null`・`: ` や `#` を含む値などは yaml 自身が引用符を付ける。`lineWidth: 0` で折り返しを止める。結果が複数行になる場合は `JSON.stringify` にフォールバック
     - flow 形式（`[&a x, ...]` / `{k: &a x}`）の中の引用符なしスカラーに `,` `[` `]` `{` `}` を含む値を平文で入れると壊れるため、引用符なし出力のうち値がこれらを含むときも `JSON.stringify` にフォールバックする（ブロック内では余計な引用符が付くだけで YAML として同値）
   - ブロックスカラー（`|` / `>`）に付いたアンカーは `range` がヘッダ〜本文全体になるので、区間ごと置換すると引用符付きスカラーになるだけで YAML として同じ値に読める。末尾の改行を含むかは実測して、含むなら置換区間の終端から末尾改行を除いて残す（実装時に1ケース確認する。本タスクの主対象はタグ名/ブランチ名で、ブロックスカラーは想定外なので、確認して問題があるときだけ対応）
   - JSDoc を実挙動に合わせて書き直す: 「アンカー付きスカラーの値の部分だけを文字列上で置換し、それ以外はバイト単位で保つ。元の引用符の種類は保つが、値が引用符なしでは YAML として別の意味に読まれる場合は引用符を付ける。空値のアンカーには半角スペース1つを挟んで書く」。`doc` は `findAnchorNode` にだけ渡す（`parseDocument` は残る）
   - `Document`/`Scalar` 以外の import に `stringify` を足す

2. `test/lib/helm.test.ts`（既存の `describe("setValueAtAnchor")` に足す。既存4件のうち「アンカー記法自体は維持」「数値に見える値」はそのまま通る想定。`vi.mock` によるライブラリの偽装はこのファイルにも `setValueAtAnchor` を使う他のテストにも無く、`grep` で確認済み。`setValueAtAnchor` を直接使うテストはこのファイルだけで、steps 側のテスト（`stage-image-tag-updates` / `stage-helm-branch-ref-updates` を参照するテスト）は実物の `helm.ts` を通るので、期待値の文字列に再シリアライズ由来の形（`{ a: 1 }`・2スペース等）が含まれていないか実装時に確認する）
   - 目的・背景の全ケースを1つの values.yaml にまとめたフィクスチャ（4スペースインデント、80桁超の文字列、`value   # comment` のように行末コメント前の複数スペース、`{a: 1}` の flow、CRLF、先頭 BOM）を用意し、書き換え後の文字列が「元の文字列の該当する値の区間だけ置換したもの」と `toBe` で完全一致することを確かめる。CRLF と BOM は別ケースにしても良い（改行を LF にした版・CRLF 版・BOM 付き版を `it.each` にする）
   - 元が `"old"`・`'old'`・引用符なし `old` の各ケースで、書き換え後に `yaml.parse` で新しい値と同じ文字列に読めること、かつ引用符の種類が保たれること
   - 特殊文字を含む新しい値（`"2027"`、`"true"`、`"a: b"`、`"# x"`、`"it's"`（単引用符ケース）、`"a,b"`（flow 内）、`"release/1.2.3"`（引用符が付かない））で、YAML として同じ値に読み戻せること
   - 空値アンカー: `tag: &a` と `- &a`（行末・ファイル末尾を含む）と `tag: &a ""` を書き換えても、`yaml.parse` で新しい値に読めて、他の行が変わらないこと
   - 既存のエラー系（アンカー無し・非スカラー）は変更なしで通ること

3. ドキュメントの追随
   - `docs/architecture.md:153` の `helm.ts` の説明（「読み書き」）と `:433` 付近の「`setValueAtAnchor()` で書き戻すとクォートが付く」の記述が、引用符の付き方（元の引用符を保つ／曖昧な値だけ付ける）と合っているかを読んで、ズレがあれば該当行だけ直す。`docs/glossary.md:112` の補足（「ASTを…」）が再シリアライズ前提の書きぶりなら同様に直す。`docs/history/` は触らない

4. 検証: `pnpm check` を通す（型チェック・lint・format:check・test）。
