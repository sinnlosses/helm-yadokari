## 目的・背景
`src/index.ts` は `run()` が投げた例外を受けて、`FatalError` なら `fatal_error` に `httpStatus` と `message` だけを、
それ以外なら `unhandled_error` に `String(err)` だけを出して `process.exit(1)` する。そのため 5xx・ネットワーク障害・
想定外の例外で落ちたとき、次のことがジョブログから追えない。

- どの chart リポジトリ・設定ユニット・アプリの処理中だったか
- どの API 呼び出し（どのプロジェクトへの何の操作）で落ちたか
- `cause` を含むスタック

致命エラーの実行ではレポートを書き出さない（`src/main.ts` の `runProcess()`、`docs/requirements.md` の該当節）ので、
手がかりはこのログしかない。

## 決まっていること（蒸し返さない）
- 致命エラーの実行でレポートを書き出さない仕様は変えない（ログで追えるようにする）
- エラーの分類（何が致命か）は変えない
- トークンなどの機微情報をログに出さない（`src/utils/logger.ts` の伏字化はトップレベルのキーにしか効かない点に注意）

## 解くべき論点
- chart・設定ユニット・アプリの文脈を、`FatalError` にどこで付けるか（`src/steps/shared/step-outcome.ts` の集約点・
  `withAppContext` など既存の文脈付けの仕組みとの関係。`src/steps/` に try/catch を書かない規約との両立）
- API 呼び出しの情報（操作・プロジェクト）を `lib/gitlab/errors.ts`・`lib/github/errors.ts` のどちらの層で付けるか
- `cause` のチェーンとスタックをどの形でログ（JSON Lines）に載せるか

## やること

### 前提の確認（2026-09-30 時点の実物）
- `src/index.ts` は背景のとおり（`fatal_error` は `httpStatus`・`message` のみ、`unhandled_error` は `String(err)` のみ）
- `FatalError` を作るのは `src/steps/shared/step-outcome.ts` の `settleAsError()`（設定ユニット単位）と `failApp()`
  （`settleApp()`＝`resolveTags()` のアプリ単位）の2箇所だけ。`rethrowWithAppContext()` は fatal を包まず素のまま投げ、
  外側の `settleAsError()` が昇格させている（アプリ名はこの時点で失われる）
- 401 は本番では `lib/platform/token-routed-adapter.ts` の `callRoute()` が素の `Error` に読み替えるので fatal に来るのは
  5xx・ネットワーク障害・タイムアウト（`GitbeakerTimeoutError`）・リトライ使い切り（`GitbeakerRetryError`）。5xx は
  `callRoute()` を素通りするので、`step-outcome.ts` に届く時点でライブラリの例外の形は保たれている
- スクラッチパッドで実物の gitbeaker にローカルの 500 サーバを当てて確かめた事実:
  - `GitbeakerRequestError.cause` は**素のオブジェクト** `{ description, request, response }` で、`request` は fetch の
    `Request`。**`util.inspect(err)` にはトークン（`PRIVATE-TOKEN` ヘッダ）がそのまま出る**。`JSON.stringify(err.cause)` は
    `{"request":{},...}` になり漏れないが情報も無い。→ `cause` は Error のものだけを辿り、素のオブジェクトは決して
    シリアライズしない
  - `cause.request.method`・`cause.request.url` は `GET http://…/api/v4/projects/42/repository/branches/main` のように
    読め、トークンはヘッダ側にしか無い
  - スタックは `at async <anonymous> (src/lib/gitlab/api.ts:140)`・`withRetry` の `runAttempt` まで辿れる（どの API
    ラッパーの何行目かは分かるが、呼び出し元の step までは辿れない）
  - ネットワーク障害の `TypeError: fetch failed` は自身の `stack` がほぼ空で、フレームは `cause`（undici の Error）側にある
    → `cause` まで載せないとスタックとして役に立たない
- Octokit の `RequestError.request` は `{ method, url, headers }` で、`authorization` ヘッダと URL の
  `access_token=`・`client_secret=` は Octokit 自身が `[REDACTED]` にしている（`@octokit/request-error` 7.1.2）

### 論点への結論
1. **文脈は `step-outcome.ts` の中で、fatal を最初に捕まえた地点で `FatalError` に昇格させて付け、外側の地点が足す。**
   - `rethrowWithAppContext()`: fatal なら素のまま投げるのをやめ、`FatalError` に昇格させて `appProjectName` を付けて投げる
     （非 fatal を `[アプリ: …]` で包む挙動は変えない）。「包むと構造が1段深くなって昇格できない」問題は、ここで昇格まで
     済ませるので起きない
   - `settleAsError()`: `err instanceof FatalError` なら設定ユニットの文脈（`chartDirName`・`unitPath`・`chartProjectId`・
     `chartProjectName`）を足して投げ直す。そうでなく `adapter.isFatalError(err)` なら従来どおり昇格させ、同じ文脈を付ける
   - `failApp()`: `withAppContext()` を通った後なので fatal は既に `FatalError`。`adapter.isFatalError` の分岐を
     `err instanceof FatalError` の投げ直しに置き換える（`resolveTags()` は設定ユニットの外なので付くのはアプリ名まで）
   - 理由: 判断は ADR 0001 のとおり `step-outcome.ts` 1ファイルに残り、`steps/` に try/catch は増えない。`withHandling()`・
     `withAppContext()` は既に全 step の入口にあるので、呼び出し側（各 step・sub-step）は1行も変わらない。
     `token-routed-adapter.ts` で昇格させる案は、ADR 0001 の「判断は step-outcome.ts の1箇所」を崩すので採らない。
     `FatalError` 以外の例外に文脈を付ける案は、`isFatalError()` が読む構造を壊すので採らない
   - 分類は変えない: fatal かどうかは今と同じ `adapter.isFatalError()` の1回の判定で決まり、昇格する地点が
     `withAppContext()` の内側に1段早まるだけ
2. **API 呼び出しの情報は、`lib/gitlab/errors.ts` と `lib/github/errors.ts` の両方に、それぞれのライブラリの形から
   `"<METHOD> <URL>"` を読む関数を置き、`PlatformAdapter` のエントリとして渡す。** ライブラリの例外の形を知ってよいのは
   各 `errors.ts` だけ（CLAUDE.md・architecture.md の責務表）で、`isFatalError`・`extractHttpStatus` と同じ経路に並べれば
   step 側がプラットフォームを知らずに済む。`api.ts` の各関数や `token-routed-adapter.ts` で操作名を付けて包む案は、
   包むと `isFatalError()` が読む構造が変わるので採らない。URL にはプロジェクト ID と操作（エンドポイント）が入り、
   トークンはヘッダにしか無いので、読むのは `method`・`url` の2つの文字列だけにする（ヘッダ・`Request` 本体には触れない）。
   HTTP 応答の無いタイムアウト・リトライ使い切り・ネットワーク障害では読めず `undefined` になるが、その場合も 3. の
   スタックに `lib/<platform>/api.ts` の行が出るので操作は追える
3. **スタックは `stack` という1本の文字列にし、`cause` を `\nCaused by: ` でつないで載せる。** 構造化した配列にしない
   のは、各要素の先頭行が `Name: message` で message と重複するうえ、`jq -r .stack` でそのまま読めるほうが調査で使う形に
   近いため。辿るのは **`Error` のインスタンスである `cause` だけ**（gitbeaker の素のオブジェクトの `cause` は
   `Request` を抱えていてトークンが入るので、そこで止める）。循環した `cause` に備えて一度見た Error で止める。
   `Error` でない値が投げられたときは `stack` を付けない（`undefined` なので JSON から落ちる）

### 変更する箇所
- `src/utils/errors.ts`
  - `FatalError` に第3引数 `context: Readonly<Record<string, unknown>> = {}` を足し、`public readonly context` で持つ
    （utils はドメインを知らないので型は汎用の record。中身はログにそのまま広げる項目）
  - `FatalError` に `withContext(extra)` を足す: `httpStatus`・`cause` を引き継ぎ、`context` は `{ ...extra, ...this.context }`
    （内側で付けた値を優先）で**新しいインスタンス**を返す（不変）
  - `toErrorStack(error: unknown): string | undefined` を足す（論点3の形。Error でなければ `undefined`、`stack` が無い Error は
    `${name}: ${message}` を使う）
- `src/steps/shared/step-outcome.ts`
  - `rethrowWithAppContext()`: `if (adapter.isFatalError(err)) throw new FatalError(adapter.extractHttpStatus(err), err, { appProjectName: projectName, request: adapter.describeFailedRequest(err) })`。
    非 Error はそのまま投げる（今と同じ）。JSDoc の「致命的エラーは包まずにそのまま投げる」の段落を、ここで昇格させて
    アプリ名を付ける旨に書き換える（`withAppContext()` の JSDoc の「そのまま投げる（アプリ名を付けない）」も同様）
  - `settleAsError()`: 先頭に `if (err instanceof FatalError) throw err.withContext(unitContext)`、続く昇格は
    `new FatalError(status, err, { ...unitContext, request: adapter.describeFailedRequest(err) })`。`unitContext` は
    `logContext` から `event` を除いた4項目を明示的に組む（`event: "update_unit"` を `fatal_error` 行へ持ち込まないため。
    分割代入で捨てる形は未使用変数の lint に掛かるので使わない）
  - `failApp()`: `if (err instanceof FatalError) throw err` に置き換える（`adapter` 引数が不要になれば外す）
- `src/lib/platform/adapter.ts`: `PlatformAdapter` に `readonly describeFailedRequest: (error: unknown) => string | undefined` を
  `extractHttpStatus` の隣に足す（JSDoc: 失敗した HTTP リクエストの `"<METHOD> <URL>"`。応答の無い失敗では undefined。
  ヘッダは読まない）
- `src/lib/gitlab/errors.ts`: `describeFailedRequest()` を足す。`error.cause.request` の `method`・`url` が文字列のときだけ
  組み立てる（`hasKey` で1段ずつ確かめる。`as` は使わない）。冒頭の「依存している構造」の列挙に `cause.request` を足す
- `src/lib/github/errors.ts`: `describeFailedRequest()` を足す。`error.request` の `method`・`url` から組み立てる
  （URL の `access_token` 等は Octokit が伏字化済みである旨を1行）
- `src/lib/gitlab/adapter.ts`・`src/lib/github/adapter.ts`: 表に `describeFailedRequest` を足す
- `src/lib/platform/token-routed-adapter.ts`: `describeFailedRequest: representative.describeFailedRequest` を足す
- `src/index.ts`:
  - `fatal_error`: `{ event: "fatal_error", httpStatus, message, ...err.context, stack: toErrorStack(err) }`
  - `unhandled_error`: `{ event: "unhandled_error", message: String(err), stack: toErrorStack(err) }`
  - ロガーの伏字化はトップレベルのキーにしか効かないが、ここで出すのは文字列の項目だけで、例外オブジェクト・`cause` の
    オブジェクトを値として渡さない（渡すと `JSON.stringify` の対象になる）
