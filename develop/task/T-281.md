## 目的・背景
`src/index.ts` は `run()` が投げた例外を受けて、`FatalError` なら `fatal_error` に `httpStatus` と `message` だけを、
それ以外なら `unhandled_error` に `String(err)` だけを出して `process.exit(1)` する。そのため 5xx・ネットワーク障害・
想定外の例外で落ちたとき、次のことがジョブログから追えない。

- どの chart リポジトリ・設定ユニット・アプリの処理中だったか
- どの API 呼び出し（どのプロジェクトへの何の操作）で落ちたか
- `cause` を含むスタック

致命エラーの実行ではレポートを書き出さない（`src/main.ts` の `runProcess()`、`docs/requirements.md` の該当節）ので、
手がかりはこのログしかない。

## 決まっていること（蒸し返さない）
- 致命エラーの実行でレポートを書き出さない仕様は変えない（ログで追えるようにする）
- エラーの分類（何が致命か）は変えない
- トークンなどの機微情報をログに出さない（`src/utils/logger.ts` の伏字化はトップレベルのキーにしか効かない点に注意）

## 解くべき論点
- chart・設定ユニット・アプリの文脈を、`FatalError` にどこで付けるか（`src/steps/shared/step-outcome.ts` の集約点・
  `withAppContext` など既存の文脈付けの仕組みとの関係。`src/steps/` に try/catch を書かない規約との両立）
- API 呼び出しの情報（操作・プロジェクト）を `lib/gitlab/errors.ts`・`lib/github/errors.ts` のどちらの層で付けるか
- `cause` のチェーンとスタックをどの形でログ（JSON Lines）に載せるか

## 完了条件
- 設定ユニットの処理中に致命エラーが起きたとき、`fatal_error` のログ行に chart リポジトリと設定ユニットを特定できる情報が入ることをテストで確かめる
- `fatal_error`・`unhandled_error` のログ行にスタック（`cause` があればそれも）が入ることをテストで確かめる
- ログにトークンが出ないこと
- ログの項目が変わるなら README（ログの説明がある節）と `docs/architecture.md` の該当箇所を追随させる
- `pnpm check` が通る
