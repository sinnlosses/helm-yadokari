## 背景

`scripts/lint/validate-config.ts:91` が設定ユニットを `accessTokenEnv` ごとに分け、そのグループの
トークンで作ったクライアントで `validateRemoteExistence()`
（`scripts/lint/remote-existence/remote-existence.ts`）を呼ぶ。projectId の実在は
`RemoteCache.hasProject`（`remote-cache.ts`）→ `projectExists()`（`src/lib/gitlab/api.ts:48`）で見ている。

`projectExists()` は `gitlab.Projects.show(projectId)` の戻り値を捨てて `true` を返すだけ。GitLab は
権限の無いプロジェクトに 404 を返すので「そのトークンでアクセスできるか」は実質検査できているが、
「どのグループに属するか」は見ていない。`config/` に namespace slug を持たせていない
（`docs/architecture.md`「その他」節）ため、所属を照合する材料がどこにも無く、グループ名は
`ACCESS_TOKEN_<グループ名>` という環境変数名の命名慣習にしか現れない。

`src/lib/config/validate.ts` の `validateAccessTokenEnvConsistency()` は、同じ projectId が2つの
`accessTokenEnv` に結びついていないかを見るローカル整合性検査で、グループとの対応は見ていない。

狙いは**トークンが想定より広いケースを捕まえること**。親グループのトークンやボットのPATに
差し替わると、アクセス可否の検査（今の「見つかりません」）は通るのに被害範囲の分離だけが静かに
壊れる。README「複数グループで運用する」のとおり gitlab.com Free では Group Access Token を
発行できずボットPATで代替する運用なので、この穴は常時開いている。

gitbeaker 43.8.0 の `Projects.show` の戻り値は `path_with_namespace: string` と
`namespace.full_path: string` を持つ（`@gitbeaker/core` の `dist/index.d.ts` で確認済み）。

## 決まっていること（蒸し返さない）

- `group` フィールドは**必須**にする（ユーザー判断、2026-09-17）。`accessTokenEnv` を必須にしたのと
  同じ理由で、書き漏らした chart が黙って検査をすり抜ける形を残さない
- 既存の `config/yadokari-smoke-test-chart/registry.yaml` と
  `config/yadokari-smoke-test-chart2/registry.yaml` にも実値を書き足す（gitlab.com の
  `sinnlosses-group`。`develop/progress.md` の「注意」参照）
- 検査するのは `validate-config --remote` だけ。本体パイプラインには入れない
- `PLATFORM=github` は `validate-config --remote` 自体が未対応なので対象外
- `config/` と `config.example/` を書き換えてコミットしてよい。push はしない

## 解くべき論点

- **前方一致の境界**。`sinnlosses-group` が `sinnlosses-group-2` に一致しないよう、セグメント単位で
  照合する（`full_path === group || full_path.startsWith(group + "/")`）。サブグループ配下を許すか
  どうかもここで決め、結論をコードのコメントかドキュメントに残す
- `path_with_namespace` と `namespace.full_path` のどちらを見るか（プロジェクト自身の path を
  含むかどうかが違う）
- `projectExists()` を所属も返す形に変えるか、別関数を足すか。`projectExists` は
  `PlatformAdapter` に含めない前例がある（`src/lib/gitlab/adapter.ts` の JSDoc）。
  **API 呼び出しの回数を増やさないこと**
- `group` のブランド型を作るかどうかと、型の置き場所（`docs/architecture.md`「型の置き場所」に従う）
- 所属違いのときのメッセージ。「見つかりません」と別の文言にする（不在・権限不足・所属違いは
  直す手が違う）
