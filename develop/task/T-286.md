## 目的・背景
`config/` のYAMLキーの語尾・形がばらついており、YAMLからコードへ詰め替えるたびに名前も変わっている。ユーザーの指示（2026-10-01）で、YAMLキーを次のとおり改名し、コード側の名前もYAMLに合わせることになった。

- versions.yaml: `helmBranchRef` → `helm`、`appBranchToSync` → `apps`
- registry.yaml: `chartToUpdate` → `chart`、`appSpecs` → `apps`、`group.groupId` → `group.id`、`group.groupName` → `group.name`

コード側の名前は `src/domain/types.ts`（`ChartRepoConfig`・`ConfigUnit.chartRepo`・`HelmConfig.branchRef`/`locations`・`AppConfig.branchToSync`/`imageTagLocations`・`AnchorLocation.anchorName`・`ConfigUnit.groupId`/`groupName`）と `src/lib/config/schema.ts`（`AppSpec`・`AnchorLocationSchema` のキー `anchor` → `anchorName` の詰め替え）にある。いまは `docs/architecture/adr/0027-config-split-by-scope.md` が「ドメイン語彙に当たる型名はYAMLのキー名に追随させない」と決めているため、この方針を見直すADRが要る。

YAMLでは versions.yaml の `helm`（値）と locations.yaml の `helm`（書き込み先）のように、キー名は1つでファイルによって中身が違う。そのため、コードの1つの型の中のフィールド名には、YAMLのキー名をそのまま写せない箇所がある。この対応をどう決めるかが本タスクの中心になる。

## 決まっていること（蒸し返さない）
- YAMLキーの改名先は上の6つで確定（ユーザー指示）。`group.name` の中身はグループのフルパスのまま
- コードとYAMLの名前が合っていないところは、コードをYAMLに合わせる（ユーザー指示）。ADR 0027 の該当方針は置き換える

## 解くべき論点
- YAMLにキー名が無い位置（versions.yaml の `helm` の値＝ブランチ名、locations.yaml の `helm[]`、`apps.<名前>` の値）を、コードのどのフィールド名にするか（例 `HelmConfig.branch`/`locations`、`AppConfig.branch`/`locations`）
- 型名（`ChartRepoConfig`・`AppSpec`・`HelmConfig`・`AppConfig`）をYAMLのキー（`chart`・registry.yaml の `apps`）に合わせるとき、registry.yaml の `apps[]` と設定ユニット側の `apps` が同名になる。この2つをコードでどう呼び分けるか
- `ConfigUnit.groupId`/`groupName` を `group: { id, name }` に入れ子にするか
- glossary の用語（「chartリポジトリ」「追跡ブランチ」「Helmの向き先ブランチ」「書き込み位置」）とコード識別子との対応をどう保つか

## やること
前提は実物で確認済み（2026-10-01、HEAD 85eafca）。`src/domain/types.ts` に `ChartRepoConfig`・`ConfigUnit.chartRepo`/`groupId`/`groupName`・`HelmConfig.branchRef`/`locations`・`AppConfig.branchToSync`/`imageTagLocations`・`AnchorLocation.anchorName` があり、`src/lib/config/schema.ts` に `AppSpec`（`z.infer`）と、`AnchorLocationSchema` の外側の `.transform()` によるキー `anchor` → `anchorName` の詰め替えがある。ADR 0027 の「コード側の識別子は外部ファイル形式の写しかどうかで追随を決める」節も記述どおり。

### 論点への結論案

決める規則は3つ。ADR 0035 の本文はこの3つと対応表で組む。

- **規則A（キーがある位置）**: YAMLのオブジェクトのキーを1対1で受けるコードのフィールドは、キー名をそのまま使う。語幹を揃えるだけでなく綴りも同じにする。ADR 0013（修飾語が無ければ型の語を持つ）・ADR 0016 の `chartRepo` の項より、この規則を優先する
- **規則B（キーが無い位置）**: versions.yaml の値（`helm` の値・`apps.<名前>` の値）と locations.yaml の配列（`helm[]`・`apps.<名前>[]`）はYAMLに名前が無いので、写す名前が無い。ここはコード側の命名規約で決め、名前は「どのファイル由来か」に揃える。locations.yaml 由来の書き込み先の配列は `locations`（`HelmConfig.locations` に `AppConfig` も揃える）。versions.yaml 由来のブランチ名は今の `branchRef`・`branchToSync` を据え置く
- **規則C（型名）**: YAMLの1つのキーの塊を写すドメイン型は `<キーの単数形>Config` と呼ぶ（既存の `HelmConfig`・`AppConfig` の形）。同じキー名が別ファイルで別の中身を持つときは、3ファイルを結合した側（ドメイン型）が素の名前を取り、1ファイルだけの写し（`lib/config/schema.ts` の `z.infer` 型・スキーマ定数）にファイル名の接頭辞を付ける（既存の `RegistryYamlSchema`・`VersionsYamlSchema` と同じ付け方）

論点ごとの結論:

1. **キーが無い位置のフィールド名**（規則B）: `HelmConfig.branchRef`/`locations` は据え置く。`AppConfig.branchToSync` は据え置き、`AppConfig.imageTagLocations` → `AppConfig.locations` に改名する
   - `locations` を揃える理由: locations.yaml の `helm` と `apps.<名前>` は同じ形（`valuesPath`+`anchor` の配列）で、YAMLは親キーだけで区別している。コードも親の型（`HelmConfig`・`AppConfig`）が用途を与えるので、ADR 0016 の但し書き（包含する型名が用途を与えるなら短い名前でよい。`helm.locations` が先例）がそのまま効く。ファイル名 `locations.yaml` とも繋がる
   - ブランチ名を据え置く理由: (a) YAMLに名前が無いので「合っていないところ」に当たらない。(b) `branch` だけにすると ADR 0013（修飾語の無い `BranchName` のフィールドは `Name`/`Ref` を持つ）に反し、`branchName` に揃えると「向き先」と「追跡」の区別がコードから消える（glossary「Helmの向き先ブランチ」が `ref` の語を選んだ理由もここ）。(c) `branchToSync` は YAMLの写しではない `TagSource.branchToSync`・`LatestTagResolution` の説明・タグ解決の15ファイルへ、`branchRef` は `HelmBranchRefUpdate`・`helmBranchRefUpdates`・`HelmBranchRefLogSummary` の語幹へ広がっており、改名がYAMLとの境界の外まで波及する。ファイル名 `versions` を写す名前はブランチ名という中身を語らないので採らない
2. **registry.yaml の `apps[]` と設定ユニット側の `apps` の呼び分け**（規則C）: 設定ユニット側＝ドメイン型 `AppConfig`（3ファイルを `projectName` で結合した結果で、`ConfigUnit.apps` の要素）は据え置く。registry.yaml の1要素の写しは `AppSpecSchema`/`AppSpec` → `RegistryAppSchema`/`RegistryApp` に改名する。`AppSpec` は旧キー `appSpecs` の写しなので、ADR 0027 の旧方針（`z.infer` 型はキー名に追随する）でも改名が要る。素の `App` を registry 側に渡さないのは、registry 側は `projectId`/`projectName`/`tagFormat` だけの部分で、appとして完結するのは結合後だから。chartリポジトリ側は `ChartRepoConfig` → `ChartConfig`、`ConfigUnit.chartRepo` → `ConfigUnit.chart`（規則A・C）
3. **`groupId`/`groupName` の入れ子**: 入れ子にする。`ConfigUnit.groupId`/`groupName` → `ConfigUnit.group: GroupConfig`（`readonly id: GroupId`・`readonly name: GroupName`）。`GroupConfig` は `src/domain/types.ts` に置く（glossary に「グループ」が載る語彙なので「型の置き場所」の1行目）。規則Aで `group.id`/`group.name` を写すとそのまま入れ子になり、使う側（実在チェック）も2つを組で扱っている。`id`/`name` は ADR 0013 の唯一の例外（包含する型が主語を与える `name`。`ParsedTag.name` と同じ）にも当たるので、規則Aとも衝突しない。ブランド型 `GroupId`/`GroupName` と、`GroupIdSchema`/`GroupNameSchema` の名前は据え置く（キーの写しではなくブランド型の名前）
4. **glossary の用語との対応**: 日本語の見出し語（「chartリポジトリ」「追跡ブランチ」「Helmの向き先ブランチ」「書き込み位置」）は変えない（ADR 0027 の「日本語の項目名とYAML・型の語の不一致は翻訳であって違反ではない」は引き続き有効）。各項の「英語識別子」欄は、規則AでYAMLキーとコードが同名になる箇所は1つにまとめて書き（例: 「chartリポジトリ」= `chart`（registry.yaml のキー、`ConfigUnit.chart: ChartConfig`））、規則Bの位置は「YAMLの位置 → コードのフィールド」の組で書く（例: 「Helmの向き先ブランチ」= versions.yaml の `helm` の値 → `HelmConfig.branchRef`、「追跡ブランチ」= versions.yaml の `apps.<app名>` の値 → `AppConfig.branchToSync`、「書き込み位置」= `AnchorLocation`（`valuesPath`・`anchor`））。見出し「chartToUpdate・appSpecs」は「chart・apps（registry.yaml）」へ、「グループ（group・groupId・groupName）」は「グループ（group・id・name）」へ T-287 で改める
