## 目的・背景
ドキュメントがコード量に比べて重く、追随漏れのコストが高い。`docs/architecture.md` は 152KB に対して `src` は約 8.5k 行、`docs/glossary.md` 44KB・`docs/requirements.md` 52KB・`docs/smoke-test.md` 36KB。実際に `docs/architecture.md`「FatalErrorは後続ステップも止める」節のような古い記述が残っていた（T-269 で直す）。
## 決まっていること（蒸し返さない）
- `/maintenance-docs` スキルの検査に沿って進める。無人（`/loop`）で進めてよい（ユーザー判断）
- `docs/history/` は対象外
## 解くべき論点
- 何を消し、何を残すか。正典の二重化・経緯の書き写し・コードから読み取れる説明を優先して削る
- 分量を減らしても、各ファイル冒頭の「節の索引」と CLAUDE.md からの参照が壊れないようにする
## やること
着手時の実測: `docs/architecture.md` 153,777B・`docs/glossary.md` 44,662B・`docs/requirements.md` 49,462B・`docs/smoke-test.md` 35,432B、`src/` は 4,962 行。`check_docs.py` は確定群0・候補群8（前回 2026-09-16 と同じ顔ぶれ）。

このタスクでは `docs/architecture.md` だけを削る（他のファイルは1コミットの説明に収まらないので後続に回す旨を報告する）。書き足しはしない。

1. 「設計判断」の各節から、適用済みの改名・移動・旧実装の経緯（「以前は〜」「後日〜に改名した」、旧名→新名の表、移行時の実測値）を削る。経緯は git log（`git log -S` で引ける）と `docs/history/` に残っている。今の形を選ぶ理由・採らなかった案・今の制約は残す
   - 対象: `validate` 統一節の旧名→新名表、`api.ts` 改名節の旧ファイルの話、`PlatformAdapter` 節の命名・移動の経緯、`config/` 2ファイル節の識別子改名表・正典更新の手順・3ファイル時代の実測、`lib/gitlab/` 節・環境変数節・MR単位節・向き先ブランチ節・入れ物の契約節・キャッシュ節・サブステップ注入節・ブランチ作り直し節・アプリ単位逐次節の「以前は」の段落、`FatalError` 節の由来
2. 「型の置き場所は`src/`全件と突き合わせて確かめてある」節を削る。件数（76件・内訳）が今の `src/`（87件）と合っておらず、書き留めた時点の突き合わせの記録にすぎないため。「表に当てはまらない型は表の側を疑う」の1文は「型の置き場所」節の箇条書きへ移す。索引の行も消す
3. 「HTTPエラーの経路」の「登場人物」表（関数名と置き場所の一覧）を削る。コードを grep すれば分かる写しで、判定の順序の箇条書きが同じ関数を名指ししている
4. 冒頭「このファイルは通読しない」のサイズの主張を削った後の実測に合わせる
5. 削った節・見出しを参照しているリンク・「節の索引」・`sed` の見出し指定（CLAUDE.md・他の docs・`src/` のコメント）を grep で確かめ、壊れていれば直す
6. `check_docs.py` を再実行して指摘が増えていないことを確かめ、`pnpm format` → `tw verify` を通す
## 完了条件
- `docs/architecture.md` を中心に、削った分量（前後のバイト数）と削った種類を `## 結果` に書く
- 削った節を参照していたリンク・索引・`sed` の見出し指定が残っていない
- `pnpm check` が通る
## 注意
1コミットで説明が付かない大きさになりそうなら、ファイル単位の後続タスクに切り出してよい。
