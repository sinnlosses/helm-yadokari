## 目的・背景
`src/lib/gitlab/errors.ts` の `isFatalError()` は、HTTP ステータスの無いネットワーク障害のうち `ECONNREFUSED`/`ENOTFOUND`/`ETIMEDOUT` だけを fatal にしている。`ECONNRESET`（接続断）・`EAI_AGAIN`（DNS の一時失敗）や undici の `UND_ERR_*` 系は fatal にならず、設定ユニットごとの `ERROR` に落ちる。GitLab 全体が落ちているときに、全設定ユニットが1件ずつ API を叩いて ERROR を積むことになる。
方針は `docs/architecture.md`「エラーは『fatalは例外・それ以外は戻り値』の2チャネル」節と「FatalErrorは後続ステップも止める」節。
## 決まっていること（蒸し返さない）
- `src/lib/github/errors.ts` は触らない（GitHub 対応は今回対象外。ユーザー判断）
## 解くべき論点
- どのコードを「全設定ユニット共通の障害」とみなすか。一時的な接続断（`ECONNRESET`）を fatal にするか、再試行（`isRetryableError()`）に回すか
## やること
実機（Node の組み込み fetch）で `TypeError: fetch failed` の `cause` の形を確認した。
- 接続拒否: `cause.code` は付かない場合がある（不正ポートでは `bad port`）。通常の拒否は `ECONNREFUSED`
- 相手が RST を返す: `cause.code = ECONNRESET`
- 応答なしで相手が閉じる: `cause` は `SocketError`、`code = UND_ERR_SOCKET`
- 不正な応答: `cause` は `HTTPParserError`（`code` なし）

方針は「ホスト全体に届かない（名前解決・接続確立の失敗）は fatal、接続確立後にリクエスト単位で起きうる切断は fatal にしない」。
1. `src/lib/gitlab/errors.ts` の fatal コードに `EAI_AGAIN`（DNS の一時失敗。`ENOTFOUND` と同じ層）と `UND_ERR_CONNECT_TIMEOUT`（接続確立のタイムアウト。`ETIMEDOUT` と同じ層）を足す。選定理由をコメントに書く。
2. 採らないコード（`ECONNRESET`・`UND_ERR_SOCKET`・`UND_ERR_HEADERS_TIMEOUT`・`UND_ERR_BODY_TIMEOUT`）は、接続確立後の1リクエスト単位の事情で起きうるため fatal にしない。`isRetryableError()` も HTTP ステータス前提なので今回は変えない。
3. `test/lib/gitlab/errors.test.ts` の `it.each` に新コードを足し、`ECONNRESET`/`UND_ERR_SOCKET` が false のテストを足す。
4. `pnpm check`（`tw verify`）を通す。
## 完了条件
- fatal とみなすコードの選定理由がコード内コメントか `docs/architecture.md` の該当節にあり、`test/lib/gitlab/errors.test.ts` で新しく足したコードの判定が確かめられている
- `pnpm check` が通る
